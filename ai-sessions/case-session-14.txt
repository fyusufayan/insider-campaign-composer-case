  2–8. Behaviour

  - Transitions:
    - Prepare is allowed from content_ready, pending_approval and approved, and
      ends in pending_approval.
    - Expiry goes from pending_approval/approved back to content_ready.
    - Draft, segmented, sending and terminal campaigns get a state error. No
      channels selected gives a 422. Content that doesn't cover the selected
      channels gives a 422 with field errors. A stale version gives a 409.
  - Schema use: only existing columns are used. prepared_at and expires_at come
    from a single clock_timestamp() reading taken after the lock, so the
    15-minute TTL is exact. The idempotency key is campaign:user:channel, and
    destination stays NULL until sending.
  - Eligibility: the new segment.CompileEligible is the one definition. It wraps
    the existing parameterized compiler and keeps a recipient for a channel
    only if they have the contact and an opted_in consent. Preparation
    recomputes the audience, writes the held rows in a single INSERT … SELECT,
    reads them back, and requires the counts and the snapshot digest to match.
    Any mismatch rolls back with a retryable error.
  - Frozen values: vars holds exactly first_name, last_name and city, copied
    verbatim. Unusable values don't remove anyone from the snapshot, because the
    snapshot must equal the audience counts. Instead, every row is
    trial-rendered and the review reports how many would fail, by reason. Those
    deliveries fail permanently at send time, as the architecture specifies.
  - Binding: the approval records segment version, a frozen copy of the rule,
    the immutable content id, channels, audience counts, snapshot count and
    digest. The content version is re-read under the lock and must be the
    newest.
  - Offer review: preparation re-runs content validation and the keyword-based
    offer check against the current content brief. Unauthorized offer or price
    findings never block preparation; they come back as a separate list for the
    approval dialog.
  - Concurrency: lock order is campaign, then approval, then deliveries. Lock,
    statement and whole-transaction timeouts are set. There is no network I/O
    inside the transaction and no LLM call anywhere in the package.

  §11.1, and tested why it's safe:

  - Stale client: a client holding the pre-expiry version can't get around any
    state check, because every check runs on the locked database row, not the
    client's view.
  - Expired approvals stay dead: no statement ever sets an approval back to
    pending or approved (a static test covers this), and a later prepare always
    creates a new approval id with new rows.
  - Nothing to reuse: an expired approval has no held rows left.
  - Stale requests are harmless: after expiry, a stale edit does what it would
    have done to the live approval (invalidates it). That edit bumps the
    version, so the rest of the stale view then gets a 409.
  - Confirmation can't succeed on an expired approval: confirm doesn't exist
    yet. The guarantee is structural: the approval is closed and has no rows,
    and the documented CP15 check requires status = 'pending' AND expires_at > 
    clock_timestamp().
  - TTLs are distinct: prepare sets the pending 15 minutes. Lazy expiry honours
    each approval's own expires_at, so an approved approval's 24 hours is
    respected; a test shows it isn't expired early.
  - Concurrent expiry and prepare: in a test running six of each, the due
    approval was expired exactly once, one prepare succeeded, and there was only
    ever one live approval.

  3. Idempotency-key uniqueness (actual schema)

  - UNIQUE (campaign_id, user_id, channel) and UNIQUE (idempotency_key) cover
    every approval of a campaign, not just one. approvals_one_live and
    approvals_one_consumed are partial unique indexes.
  - Re-preparing reuses the identical keys. This works because the old
    approval's held rows are deleted in the same transaction before the new rows
    go in, and the new rows carry the new approval id.
  - The tests show inserting a duplicate is rejected by each of these
    constraints.
  - Once a snapshot has been released for sending, the campaign can't be
    prepared again, so its rows are permanent and each key belongs to exactly
    one sent snapshot. The key format is unchanged.
  - Defect found and fixed: a sending campaign keeps active_approval_id pointing
    at its consumed approval (§4). Lazy expiry treated that as an
    inconsistency, so ExpireDue or prepare on a sending campaign returned an
    internal error. Now it's a no-op for ExpireDue and a clean state error for
    prepare.

  4. Consent changes during preparation

  - Defect found and fixed: the partition shown to the marketer and the expected
    recipient set were computed by two separate statements, so the non-eligible
    counts could describe a slightly different moment from the frozen rows.
  - Fix: the new segment.ComputeSnapshotAudience returns the partition plus the
    eligible counts and digest from one statement, so one database snapshot.
    Eligibility is now derived from the same classification CTE that the
    statistics count.
  - Guarantee: the committed held rows are exactly the eligible cell of the
    stored partition at one instant. Any change committed between that statement
    and the insert alters the digest (even when counts match) and rolls
    everything back with a retryable error. A trigger-injected test covers three
    cases.
  - No customer rows are locked and the isolation level is unchanged.
  - Rechecked at send time: consent on every attempt, and the current contact at
    the first attempt. Membership is never re-evaluated and vars stay frozen.

  5. Offer findings and channel content

  - Offer and price findings are in Summary.Review.OfferFindings. They're
    advisory at prepare, and §9.1 now states the CP15 requirement that the
    dialog shows them before Confirm.
  - Every selected channel must have content, or prepare returns 422.
  - Text for an unselected channel is a channel_not_selected warning and is
    never frozen.
  - The approval binds the current, newest content id and segment version under
    the lock (tested).

  The correction

  - Same transaction: expiry moves the approval to expired, deletes its held
    rows, sets the campaign to content_ready, clears the active approval pointer
    and bumps the version by one, all together. The campaign-update helper now
    refuses any approval transition that doesn't bump by exactly one.
  - No-ops write nothing: an expiry check with nothing due doesn't touch the
    row, so neither the version nor updated_at changes.
  - Sending and finished campaigns are skipped, even when the consumed
    approval's old expires_at has passed. Only pending_approval and approved
    campaigns have a live approval to expire.
  - Lazy expiry is now committed first, in its own transaction, before the
    prepare transaction runs. The new bump made this necessary:
    - If expiry and its bump happened inside the prepare transaction, a stale
      client's version check would fail and roll the expiry back with it.
    - The client could then retry forever against an approval that stays expired
      but is never closed.
    - Now a prepare using the pre-expiry version gets a 409 while the expiry
      stays committed; the client reloads and proceeds.
    - If an approval becomes due between the two transactions, the prepare
      transaction expires it, gets a 409, and rolls back. It never supersedes
      it.
  - Kept as before: the approved-vs-pending TTL distinction, the refusal to
    re-prepare a still-approved campaign, and the single-statement audience
    snapshot with digest check.
  - Docs: the no-bump exception is removed from §11.1 and §9.1, and expiry is
    shown as a version+1 write in §5.2 and §5.5. The approved refusal is
    documented as the deliberate product-safe deviation from the §5.2 table.
