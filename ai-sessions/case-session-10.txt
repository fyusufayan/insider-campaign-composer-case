    leaving it out; a model that doesn't support it fails with a 400 instead of
    silently running without thinking.
  - Defaults are unchanged.

  5. Response and stop reasons

  - Text blocks are joined together and thinking blocks are skipped.
  - Any other block type, or end_turn with no text, is treated as an error and
    never used as output.
  - end_turn, max_tokens, refusal and stop_sequence map to their existing
    constants. Any other stop reason is passed through unchanged, and the
    interpreter rejects it.
  - Each response keeps the served model, input/output tokens, the request-id
    header and the measured latency.

  6. Errors and retries

  - Not retryable (rejected): 400 (including schema rejection), 401, 403,
    404, 413.
  - Retryable (unavailable): 408, 409, 429, 5xx and network errors.
  - Cancellation or deadline: returned as the context error.
  - Status code and request ID are kept. The error message is rebuilt from
    status, error type and request ID only, because the SDK's own error string
    includes the raw response body.
  - SDK automatic retries: connection errors, 408, 409, 429 and 5xx, up to
    CLAUDE_MAX_RETRIES times. Backoff starts at 0.5s and doubles, capped at 8s
    with jitter.
  - One time budget: the interpreter's timeout covers all attempts. A server
    retry-after header is honoured without a cap, so a long one simply ends in a
    timeout.
  - One deviation from ARCHITECTURE §7.1: I don't set a per-attempt timeout. The
    SDK retries an attempt that times out, which would throw away and pay again
    for a slow but healthy generation. ARCHITECTURE and the ADR now say this.
  - Worst case per interpretation: 3 model requests (first answer, one repair,
    one truncation retry), each with up to 3 HTTP attempts, all inside the 45s
    timeout.

    start.

    the README says how to create the counter.
