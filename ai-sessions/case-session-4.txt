  2. DSL and public API

  - Rule types: Rule{Version, Match, Conditions, Groups} and Group{Match, 
    Conditions}. Groups can't contain groups.
  - Conditions: Condition is a sealed interface with three types:
    AttributeCondition, EventCondition (Count *int, CategoryIn []string) and
    BehaviorCondition. Each one writes its type field when encoded.
  - Values: Value{Kind: String|Strings|Int|Range}. Each operator needs one fixed
    value shape.
  - Entry points:
    - Decode(data) (Rule, error) checks shape only.
    - Validate(Rule) Errors checks the meaning.
    - Normalize(Rule) (Validated, error) validates, then normalizes.
    - Parse(data) (Validated, error) runs the whole pipeline.
  - Registry (for the CP5 prompt and schema): Fields(), LookupField,
    Categories(), Operators(), EventNames(), EventOps(), BehaviorPredicates(),
    ConditionTypes(), MatchValues(). All of them return copies.
  - Validated: its only field is unexported. The zero value reports IsZero(),
    and encoding it fails with ErrNotValidated. UnmarshalJSON runs the full
    Parse, so a rule loaded from the database is always validated again. Rule()
    returns a deep copy. The CP4 compiler will live in the same package and
    should accept only a non-zero Validated.

  3. Strict decoding

  Rules are not decoded with encoding/json into structs. jsontree.go reads the
  input token by token (json.Decoder.Token) and builds a small tree. The decoder
  then checks every object against its own list of allowed properties,
  separately for each condition type.
  - Rejected: unknown properties, duplicate keys, null anywhere, numbers that
    aren't integers (including 1.0 and 1e1), integers outside the 32-bit range,
    invalid UTF-8, trailing data, nesting deeper than 8, input over 64 KiB, and
    nested groups (nested_groups_not_supported).
  - Embedded rules stay strict: Rule.UnmarshalJSON also goes through this
    decoder. A test confirms that a rule inside an envelope decoded with
    DisallowUnknownFields still rejects unknown and duplicate properties and
    nested groups.
  - Error shape: each error is {path, code, message, allowed?}, the same JSON
    shape as httpapi.FieldError, with paths like groups[1].conditions[0].value.
    WithPrefix("segment") is there for CP5 envelopes. Messages never repeat the
    input back.

  4. Validation and normalization

  - Validation: Validate is the single validator for every source, and it
    re-checks everything Decode checks. It covers:
    - the field allow-list and operator per field;
    - the value shape for each operator;
    - number ranges, and invalid_range when between has min > max;
    - count being required with count_gte/count_lte and forbidden with
      exists/not_exists;
    - within_days from 1 to 365;
    - list sizes of 1 to 50, at most 10 conditions per group, at most 5 groups,
      and at least one condition overall;
    - known cities, ISO 3166-1 alpha-2 country codes (all 249), gender, language
      and product category.

    Invalid conditions are reported, never dropped, and errors always come out
    in the same order.
  - Consent: any field, condition type, event or predicate that names consent or
    contact data (sms_consent, email, phone, opted_in, kvkk…) is rejected with
    consent_is_backend_enforced.
  - Normalization:
    - Sets version: 1.
    - Cities become catalog keys (İZMİR, İzmir → izmir); country codes become
      upper case; gender, language and category values become lower case.
    - in lists and category_in are sorted and de-duplicated; condition and group
      order is kept.

    It's idempotent, and the stored form decodes back to an identical rule.

  5. Security properties and limitations

  - Only the listed fields can ever reach a rule. Field names are allow-list
    keys, never column names.
  - Values pass only through catalog lookups, so injection strings come back as
    unknown_city, not_allowed and so on.
  - Input size and nesting depth are capped.

  Limitations:
  - The consent/contact check matches substrings. A false negative still gets
    rejected as unknown_field, just with a less specific code.
  - Only the one contradiction inside a single condition is detected (between
    with min > max). Contradictions across conditions (e.g. city eq A AND city 
    eq B) aren't, because the architecture doesn't require it.
  - Validate returns Errors. Assigning a nil result to a variable of type error
    makes it non-nil, so callers should compare the Errors value itself.

  7. Architectural deviations

  None in the design, but the architecture left a few things open, so I wrote
  these choices into §6.1:
  - between takes {"min","max"}, inclusive.
  - version is optional on input.
  - A rule needs at least one condition.
  - String values are matched without regard to case.
  - category_in only accepts the 8 seed categories.

  That last one is my own addition so a typo can't silently match nobody. The
  list is copied in registry.go from cmd/seed, and no test checks that the two
  stay the same, since that test would sit in the seed package and outside CP3's
  scope. The architecture also doesn't define how count_lte treats users with
  zero events; that's for CP4 to decide.
