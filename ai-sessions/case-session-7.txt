❯ We are continuing Smart Campaign Composer development.                        
  CP1–CP5 are complete, reviewed, tested, and committed. Begin CP6 — Campaign   
  API, Persistence, Interpretation and Audience Preview in Slice 1a.            
  Follow CLAUDE.md and the finalized design documents.                          
  Read the relevant sections of docs/ARCHITECTURE.md (campaign lifecycle, HTTP  
  API contracts, data model, transactions, interpretation persistence and       
  audience statistics), applicable ADRs, and the CP6 roadmap requirements.      
  Reuse existing code rather than introducing alternative validation or query   
  paths.                                                                        
  Important: Treat the documented HTTP methods, paths, request/response shapes, 
  version semantics and status transitions as authoritative. Do not invent      
  competing contracts from the examples below.                                  
  Objective                                                                     
  Connect the already implemented components into a working, persistent backend 
  workflow:                                                                     
  HTTP request → Campaign service → PostgreSQL persistence → AI interpretation  
  → Validated segment → Audience preview → HTTP response.                       
  No frontend yet. No approvals, delivery queue, mock sending or live Anthropic 
  integration.                                                                  
  1. Campaign domain and repository                                             
  Implement the minimum campaign domain model, repository and service required  
  by the CP6 API.                                                               
  Support the documented draft lifecycle and the relevant fields from the       
  existing campaigns schema:                                                    
                                                                                
  * ID, name, brief, status and selected channels.                              
  * Segment rule and segment_version.                                           
  * Interpretation metadata and content_brief.                                  
  * Optimistic-concurrency version.                                             
  * Created/updated timestamps and other relevant read fields.                  
                                                                                
  Reuse the existing database pool and error conventions.                       
  Keep SQL parameterized and avoid leaking DB internals into the HTTP API.      
  Do not add migrations unless a real schema blocker is demonstrated.           
  2. Campaign API                                                               
  Implement the CP6 endpoints from the architecture, including the documented   
  equivalents of:                                                               
                                                                                
  * Create a draft campaign.                                                    
  * Get campaign details.                                                       
  * Update editable draft fields.                                               
  * Interpret the campaign brief.                                               
  * Preview the matched audience and exclusive channel partitions.              
                                                                                
  Use the exact route names, verbs, input types and response envelopes defined  
  in the documents.                                                             
  Validate:                                                                     
                                                                                
  * Campaign names and brief lengths.                                           
  * UUID route parameters.                                                      
  * Channels and their canonical ordering.                                      
  * Required and forbidden request properties.                                  
  * JSON types, trailing data and unknown fields.                               
  * Optimistic-concurrency expectations.                                        
                                                                                
  Reuse existing HTTP middleware for request IDs, error envelopes, recovery and 
  logging.                                                                      
  Ensure internal errors do not expose secrets, raw LLM output, database URLs   
  or customer contact data.                                                     
  3. Interpretation transaction boundaries                                      
  A network LLM call must never run while holding a PostgreSQL transaction or   
  row lock.                                                                     
  Use a safe workflow:                                                          
                                                                                
  1. Read the campaign and capture the relevant versions/state.                 
  2. Call the Interpreter outside any database transaction.                     
  3. Validate the resulting interpretation and segment through the existing     
  pipeline.                                                                     
  4. Open a short transaction.                                                  
  5. Recheck campaign state and relevant version(s).                            
  6. Persist the interpretation, normalized segment and content brief           
  atomically if still current.                                                  
  7. Commit, otherwise return the documented version-conflict response.         
                                                                                
  If the user changes the brief or other interpretation-sensitive state while   
  AI processing is in progress, stale AI output must not overwrite newer edits. 
  On LLM failure, refusal, invalid output, cancellation or a failed repair,     
  preserve the previously committed campaign state.                             
  Apply the documented initial-channel decision:                                
                                                                                
  * On the first successful interpretation only, copy suggested_channels into   
  channels if `segment_version == 0` and the persisted channels are still       
  empty.                                                                        
  * Subsequent interpretations must never overwrite explicit user channel       
  selections.                                                                   
  * A user must be able to intentionally select an empty channel list.          
                                                                                
  Be careful not to treat an empty list as permission to overwrite the user's   
  explicit choice later.                                                        
  4. Campaign and segment versions                                              
  Implement the exact documented lifecycle and version rules.                   
  At minimum:                                                                   
                                                                                
  * Campaign.version supports optimistic concurrency.                           
  * Segment_version advances according to the architecture's rules when the     
  stored normalized segment changes.                                            
  * No accidental version bump on a read.                                       
  * No lost updates under concurrent requests.                                  
  * Repeated AI interpretations must not accidentally reset channels or other   
  user decisions.                                                               
  * Status transitions must be validated rather than accepting arbitrary        
  client-provided status.                                                       
                                                                                
  Where the documents distinguish campaign version from segment version,        
  preserve that distinction.                                                    
  5. Audience preview                                                           
  Use the existing `segment.AudienceRepository` and compiled validated rules.   
  Do not write another SQL compiler or a second implementation of consent and   
  contact checks.                                                               
  Return:                                                                       
                                                                                
  * Matched user count.                                                         
  * Per-selected-channel eligible, no_consent and no_contact counts.            
  * Reach partition.                                                            
  * Total eligible messages.                                                    
  * The documented computed-at timestamp and metadata.                          
                                                                                
  Preview must be read-only.                                                    
  Handle:                                                                       
                                                                                
  * Campaign with no validated segment.                                         
  * Empty selected channels.                                                    
  * Rules with no matches.                                                      
  * Invalid channels.                                                           
  * Cancelled or timed-out queries.                                             
                                                                                
  A preview is informational and must not create delivery rows or imply that an 
  audience has been approved or frozen.                                         
  6. Tests                                                                      
  Docker-independent unit and HTTP tests                                        
  Use mocks/fakes for service dependencies and Scripted LLM where appropriate.  
  Test:                                                                         
                                                                                
  * Create, get and update request validation.                                  
  * Unknown JSON properties and wrong types.                                    
  * Invalid UUIDs and missing campaigns.                                        
  * Version conflict mapping.                                                   
  * Invalid campaign state transitions.                                         
  * First-interpretation channel defaulting.                                    
  * User-supplied empty channels and subsequent interpretation.                 
  * Failed interpretation preserves existing data.                              
  * Repair success through the API.                                             
  * Refusal, truncation, unsupported demo targeting and provider failure        
  mapping.                                                                      
  * Response envelopes, request IDs and safe error messages.                    
                                                                                
  PostgreSQL integration tests                                                  
  Use the existing Testcontainers infrastructure and integration build tag.     
  Test the real HTTP → service → database path where practical.                 
  Include:                                                                      
                                                                                
  * Successful create → interpret → preview → get.                              
  * Persisted normalized segment survives database readback.                    
  * Segment and campaign version behavior.                                      
  * Two concurrent updates with the same expected version: exactly one          
  succeeds.                                                                     
  * A brief update racing a long-running scripted interpretation: stale AI      
  output is rejected, not persisted.                                            
  * No database transaction remains open while the scripted LLM is blocked.     
  * No contact or consent values appear in API responses.                       
  * Empty channels produce zero eligible messages while preserving matched      
  users.                                                                        
  * Invalid/failed interpretation leaves the previous committed state intact.   
  * Audience preview counts agree with the existing independently tested        
  segment repository.                                                           
                                                                                
  Avoid sleeps for concurrency ordering. Use explicit synchronization signals,  
  transaction/lock observations and bounded deadlines.                          
  7. Wiring and configuration                                                   
  Wire the services and handlers into `cmd/api` using the existing              
  configuration and provider-selection rules.                                   
                                                                                
  * No key → demo mode works.                                                   
  * Anthropic mode without the real client remains explicitly unsupported at    
  this stage.                                                                   
  * Do not silently fall back to demo after a provider error.                   
  * No new infrastructure or API credentials are needed for this checkpoint.    
                                                                                
  Expose only the endpoints already authorized by CP6.                          
  8. Scope boundaries                                                           
  Do not implement:                                                             
                                                                                
  * CP7 Vue frontend.                                                           
  * CP8 Docker Compose orchestration.                                           
  * Content generation or streaming.                                            
  * Approval prepare/confirm/send.                                              
  * Delivery worker, retries, rate limiting or mock provider.                   
  * Real Anthropic API calls.                                                   
  * Any paid API request.                                                       
                                                                                
  Keep the design modular, straightforward and focused on the current vertical  
  slice.                                                                        
  9. Verification                                                               
  Run:                                                                          
                                                                                
  * `make test`                                                                 
  * `go test -race ./...`                                                       
  * `make test-integration`                                                     
  * `make lint`                                                                 
                                                                                
  If staticcheck download fails with the existing TLS certificate issue,        
  clearly distinguish that infrastructure failure from actual static analysis   
  findings. You may use the already cached pinned version without weakening     
  security checks for dependency downloads.

  Report:                                                                       
                                                                                
  1. Files created or modified.                                                 
  2. Exact HTTP endpoint contracts.                                             
  3. Campaign service/repository public APIs.                                   
  4. Transaction and optimistic-concurrency design.                             
  5. First-interpretation and user-selected-channel behavior.                   
  6. HTTP and PostgreSQL integration tests with results.                        
  7. A concrete successful demo workflow, with request/response examples.       
  8. Remaining limitations or architectural deviations.                         
                                                                                
  Do not commit anything.

  2. Endpoint contracts (base /api/v1)

  Request: POST /campaigns {name, brief}
  Success: 201 campaign + Location
  Errors: 422, 415
  ────────────────────────────────────────
  Request: GET /campaigns/{id}
  Success: 200 campaign
  Errors: 422 bad UUID, 404
  ────────────────────────────────────────
  Request: POST /campaigns/{id}/interpret (empty body or {})
  Success: 200 {campaign, audience, audience_error?}
  Errors: 404, 409 invalid_state/version_conflict, AI errors below
  ────────────────────────────────────────
  Request: GET /campaigns/{id}/audience
  Success: 200 {campaign_id, campaign_version, segment_version, channels, 
    audience}
  Errors: 409 in draft, 503 audience_unavailable
  ────────────────────────────────────────
  Request: PUT /campaigns/{id}/channels {channels, expected_version}
  Success: 200 campaign
  Errors: 422, 409
  ────────────────────────────────────────
  Request: GET /readyz
  Success: 200 with database, migration version and llm_provider
  Errors: 503 not_ready

  - Campaign shape: id, name, brief, status, channels, segment_rule|null, 
    segment_version, interpretation|null, content_brief|null, version, 
    created_at, updated_at.
  - AI error mapping:
    - llm_unavailable: 503, retryable
    - llm_refused: 422
    - llm_truncated: 502
    - llm_rejected: 502
    - ai_output_invalid: 422, with details and raw_proposal, as §7.5 requires
    - invalid_brief: 422
  - Unknown errors return a fixed 500 internal server error. The cause goes only
    to the masked log.

  3. Public APIs

  - Service: Create, Get, SetChannels(id, channels, expectedVersion),
    Interpret(id) → InterpretResult, Audience(id) → AudiencePreview.
  - Repository: Create, Get, Update(id, Mutation). Update locks the row, applies
    a pure mutation, writes the result guarded by version, and commits.
  - Pure transitions: WithInterpretation(observedVersion, in),
    WithChannels(expectedVersion, chs), and
    Check{Interpret,SetChannels,Audience}.

  4. Transactions and concurrency

  1. Interpret reads the campaign without a lock and remembers its version.
  2. The model is called with no transaction open.
  3. One short transaction (5 s lock and statement timeouts) locks the row with
     FOR UPDATE and rechecks status and version. If anything changed while the
     model was working, it returns 409 version_conflict and the AI output is
     discarded.
  4. The audience is then computed from the committed row, in the existing
     read-only AudienceRepository transaction.

  Version rules:
  - version goes up by 1 on every write. Reads never change it, and a no-op
    channel update doesn't either.
  - segment_version goes up only when the stored normalized rule actually
    changes. A respelled but identical rule does not bump it.

  5. Channels

  - Channels are copied from suggested_channels only when segment_version == 0
    and the channel list is empty, which means the first interpretation only.
  - Draft campaigns can't call PUT /channels. So once a user can choose
    channels, segment_version is already ≥ 1, and an explicit [] is never
    overwritten. Tests cover this.
  - Input is de-duplicated and stored in canonical order (sms, email).

  8. Deviations and limitations

  - No brief or name edit endpoint. The documents define none, so I didn't
    invent one. The brief race is tested with the only documented edit, PUT 
    /channels. The version check would cover a future brief edit the same way.
  - Interpret and channel edits are refused in pending_approval/approved. §5.2
    allows them, but that requires revoking the approval, which doesn't exist
    until Slice 3. This state can't be reached in CP6.
  - API details the documents don't specify:
    - an invalid UUID returns 422, not 404;
    - new codes: audience_unavailable (503), request_cancelled (499),
      unsupported_media_type (415);
    - the interpret response includes audience_error when the audience query
      fails after the interpretation was committed;
    - GET /campaigns (list) isn't implemented;
    - the detail view omits content, approval and delivery sections, which don't
      exist yet.
  - Store interface. I added it as a test double so the service and HTTP tests
    run without Docker. The repository itself stays concrete and is tested
    against PostgreSQL.
  - Docs. docs/ARCHITECTURE.md hasn't been updated with these clarifications
    yet.
