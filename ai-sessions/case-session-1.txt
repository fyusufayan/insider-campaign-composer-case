  1. Product Overview                                                           
  Smart Campaign Composer is an AI-powered marketing campaign creation          
  platform.                                                                     
  A marketing user describes a campaign in natural language.                    
  Example:                                                                      
  “Send a short and friendly 30% discount reminder to users in Istanbul who     
  added products to their cart in the last 30 days but did not complete a       
  purchase.”                                                                    
  The application should:                                                       
                                                                                
  1. Interpret the marketing brief using Claude.                                
  2. Generate a structured audience segmentation rule.                          
  3. Validate the segmentation rule on the backend.                             
  4. Calculate and display the estimated audience size.                         
  5. Generate SMS and email content.                                            
  6. Stream generated content to the frontend.                                  
  7. Allow the marketer to preview and edit the content.                        
  8. Require explicit human approval before sending.                            
  9. Send messages asynchronously through a mock provider.                      
  10. Display live campaign delivery statistics.                                
                                                                                
  No real messages will be sent. We will create a few thousand fake users and   
  implement our own mock SMS/email provider.                                    
  2. Required Technologies                                                      
                                                                                
  * Frontend: Vue.js (prefer Vue 3 + TypeScript)                                
  * Backend: Go                                                                 
  * LLM: Anthropic Claude API                                                   
  * Database: PostgreSQL                                                        
  * Containerization: Docker and Docker Compose                                 
  * Testing: Go testing and appropriate Vue testing tools                       
  * Streaming: Server-Sent Events (SSE) is our initial preference for live      
  updates.                                                                      
  * Queue: Evaluate a PostgreSQL-based job queue before introducing additional  
  infrastructure such as Redis.

⏺ Smart Campaign Composer: Architecture and Technical Plan

  Repository state: the repo is empty. It has a main branch, no commits and no
  files, so this plan assumes nothing already exists. I haven't changed
  anything.

  SDK check: the official Go SDK (github.com/anthropics/anthropic-sdk-go) is
  maintained and covers everything we need:
  - streaming (Messages.NewStreaming plus Accumulate)
  - structured JSON output (output_config.format)
  - reading the key from ANTHROPIC_API_KEY
  - built-in retries for 429, 5xx and connection errors (default 2)

  So we don't need raw HTTP. The default model is claude-opus-5-5, set by an env
  var. Three things about this model change the design:
  - Forced tool_choice returns a 400. So we get JSON through structured outputs,
    not a forced tool call.
  - Thinking can't be turned off. We control depth with effort instead.
  - A response can end with stop_reason: "refusal". We must handle that case.

  The backend is a modular monolith: one Go module, one Docker image, three
  entrypoints.
  - api and worker are separate processes because they fail and scale
    differently. A slow LLM stream must never starve delivery, and a worker
    crash must not take the UI down. They share the domain packages and the
    database.
  - The mock provider is a separate HTTP service, not an in-process fake. The
    requirements we're graded on (429 handling, timeouts, idempotency, rate
    limits) only mean something across a real network boundary. It also lets us
    prove from outside that no duplicates were sent. An in-process fake is still
    used in unit tests.
  - PostgreSQL is the only infrastructure. No Redis or broker; the reasoning is
    in §6.

  Non-functional

  - Throughput: at most 100 msgs/s per channel, enforced on our side and not
    just tolerated through 429s.
  - Responsiveness: the first streamed token shows up in under ~2 s; a stats
    update reaches the UI within about 1 s.
  - Operability: docker compose up brings everything up, with seed data and the
    mock LLM when no key is set.
  - Determinism: seed data is generated from a fixed RNG seed, so demos and
    tests are reproducible.
  - Maintainability: handlers stay thin, business rules live in services, and
    the code is organized by feature.

  AI-specific

  - LLM output is untrusted input. It goes through schema validation and then
    semantic validation, every time.
  - The LLM never produces SQL, and never sees user data (no PII in prompts).
  - The real client and the mock share one interface. Tests run without a key.
  - Every LLM call is recorded: prompt version, model, raw output, parsed
    output, validation errors, tokens, latency.
  - Failures are handled explicitly: malformed JSON, truncation (max_tokens),
    refusal, timeout, a stream cut mid-way, and output that's valid JSON but
    semantically wrong.
  - Parts of a brief we can't express are surfaced, not dropped. The model
    returns unsupported[] and assumptions[].

  Reliability

  - Delivery is at-least-once, with idempotency keys that make it
    effectively-once whenever the provider honours them. The honest guarantees
    are in §6.
  - A database constraint (UNIQUE(campaign_id, user_id, channel)) blocks
    duplicates structurally.
  - Leases on claimed jobs mean a crashed worker's in-flight work gets picked up
    again.
  - Retries use classified errors, exponential backoff with jitter, and
    Retry-After.
  - Sending a campaign is idempotent: a double-click or retry doesn't enqueue it
    twice.

  Security

  - SQL: parameterized queries only. Column identifiers come only from a
    compile-time registry.
  - Templates: our own minimal {{var}} substitution, not Go text/template, which
    would let LLM output run template actions.
  - XSS: LLM output is never put in the DOM with v-html. The email preview
    renders escaped text inside a sandboxed iframe.
  - Secrets: API key from the environment only, never logged. Request logs mask
    phone numbers and emails.
  - Input validation: every HTTP body is validated, with size limits on the
    brief (e.g. 2,000 chars) and on content.
  - Consent: the backend always enforces it. The DSL can't refer to it, so the
    LLM can't loosen it.
  - Auth: out of scope. One hard-coded "marketer" identity is recorded as
    approved_by; documented as a limitation.

  Acceptance criteria (abridged, testable)

  1. Given the example brief, the system produces a valid rule (Istanbul + cart
     in the last 30 days + no purchase since) and shows its interpretation and a
     non-zero audience count split by channel.
  2. A rule that uses an unknown field or operator, a wrong value type, or
     out-of-range bounds is rejected with a structured error (path, code,
     message). No SQL is run.
  3. Users without consent for a channel, or without a contact address for it,
     are never counted for that channel and never enqueued for it.
  4. SMS text that could exceed 160 characters after personalization, or an
     email subject over 80, can't be approved.
  5. send on a campaign that isn't approved returns 409. After approval, editing
     content resets the campaign to un-approved.
  6. Calling send twice, or running 4 workers at once, never produces more than
     one provider-accepted message per (campaign, user, channel).
  7. No 1-second window has more than 100 provider calls per channel.
  8. Transient failures and 429s are retried. Permanent failures are marked
     failed with the reason. The campaign reaches a final state.
  9. The dashboard updates live without a page reload and recovers after the
     network drops.
  10. go test ./... and npm test pass without ANTHROPIC_API_KEY.

  Ambiguities (proposed defaults; please confirm)

  Ambiguity: What "did not complete a purchase" means: no purchase after the 
  cart
   add, or no purchase in 30 days?
  Proposed default: Provide a dedicated predicate, abandoned_cart: a cart event
  in the window with no purchase at or after it. The LLM states which reading
  it chose in assumptions[].
  ────────────────────────────────────────
  Ambiguity: A user who consents to both channels: do they get both?
  Proposed default: Yes, for each channel the marketer selects. Each (user,
  channel) is tracked separately. The UI shows the overlap.
  ────────────────────────────────────────
  Ambiguity: How "160 characters" is counted
  Proposed default: Unicode characters (runes) after rendering, using worst-case

  variable lengths. The UI also warns that Turkish characters (ş, ğ, ı) force
  UCS-2 encoding, where one segment is 70 characters; that's information, not a
   blocker.
  ────────────────────────────────────────
  Ambiguity: Are an unsubscribe footer and SMS opt-out text required?
  Proposed default: The backend appends a fixed email footer, outside the LLM's
  text. SMS: optional "STOP" suffix counted inside the 160, behind a config
  flag (off by default).
  ────────────────────────────────────────
  Ambiguity: When the audience is decided
  Proposed default: The estimate is computed when previewed. The snapshot is 
  taken at send time, from the same rule, and the UI shows the difference.
  Consent is checked again just before each send.
  ────────────────────────────────────────
  Ambiguity: What "last N days" is measured against
  Proposed default: Send/preview time, now() - N days, in UTC. Documented.
  ────────────────────────────────────────
  Ambiguity: Can the marketer edit the segment rule?
  Proposed default: Yes, through a structured form editor (dropdowns over the
  allow-list), validated the same way as LLM output. Low cost, and a good
  fallback when the LLM gets it wrong.
  ────────────────────────────────────────
  Ambiguity: Cancelling a campaign mid-send
  Proposed default: Stretch goal: cancel flips pending deliveries to cancelled.
  In-flight ones finish.

  Edge cases that are easy to miss

  - City spelling: "İstanbul" vs "Istanbul" vs "istanbul". Turkish
    dotted/dotless i breaks a naive strings.ToLower. Store city_normalized and
    match against a known-cities list.
  - Audience of zero: sending is blocked, and the UI explains why.
  - Very large audience: we don't paginate the snapshot because we only have a
    few thousand users; the scaling path is documented.
  - Empty first name: fallback syntax {{first_name|there}}, or a default per
    variable.
  - Variables: unknown ones like {{coupon}} are rejected; malformed ones ({{ 
    first_name }) are detected.
  - LLM output: it may put the discount in the SMS but not the email, or invent
    a different discount (40%). The offer check is a warning, not a blocker.
  - Concurrent edits: two tabs editing the same campaign. Optimistic concurrency
    with a version column.
  - Consent revoked after enqueue: re-checked at dispatch, giving status
    skipped_no_consent.
  - Provider timeout: a timeout is ambiguous: the provider may have sent the
    message. Retry with the same idempotency key.
  - Worker crash: after the provider accepts but before our DB commit. Covered
    by the lease plus the idempotency key; see §6.
  - Client disconnects during generation: cancel the Claude call. Persist the
    result only if it completes.

  - the repositories behind the worker and the campaign service, so the state
    machine can be unit-tested

  We won't add an interface per repository by reflex. Integration tests hit real
  Postgres.

  Campaign state machine

  draft ──interpret──▶ segmented ──generate/edit content──▶ content_ready 
  ──approve──▶ approved ──send──▶ sending ──▶ completed
    ▲                     │  ▲                                  │   ▲           
          │                       └──▶ completed_with_failures
    └──────(edit brief)───┘  └────────(edit segment)────────────┘   └──(edit 
  content)────┘ (edit = un-approve)
                                                                         any 
  pre-send state ──cancel──▶ cancelled
  Transitions are compare-and-set in SQL, for example UPDATE … SET 
  status='sending' WHERE id=$1 AND status='approved'. That makes them safe under
  concurrency, and it's what makes send idempotent.

  Streaming mechanism

  Both streams use SSE. They differ in how they reconnect:
  - Content generation: the request is POST /campaigns/{id}/content/generations
    and the response is an SSE stream (text/event-stream). The frontend reads it
    with fetch() plus a ReadableStream parser, because EventSource can only do
    GET. We don't reconnect: generation is tied to the request, a disconnect
    cancels the Claude call, and the user clicks Regenerate.
  - Delivery status: GET /campaigns/{id}/events uses a plain EventSource. Every
    event is a full snapshot of the stats, not a diff, so reconnecting needs no
    replay or Last-Event-ID bookkeeping. The server polls an aggregate query
    once per second per open stream, and sends a heartbeat comment every 15 s.
  - Why polling instead of LISTEN/NOTIFY: at our scale it's trivially cheap, it
    works with multiple API instances, and it can't miss events. LISTEN/NOTIFY
    is the documented upgrade path.

  Frontend modules

  These are covered in §8.

  How we guarantee "not sent twice":
  1. Enqueue level. UNIQUE(campaign_id, user_id, channel) plus INSERT … SELECT …
     ON CONFLICT DO NOTHING. Even if enqueue runs twice, there is one job per
     recipient per channel.
  2. Campaign level. The approved → sending change is compare-and-set, and
     enqueueing happens in the same transaction. Only one send call can ever
     enqueue.
  3. Claim level. FOR UPDATE SKIP LOCKED plus a lease. Two workers can't hold
     the same row at once.
  4. Provider level. The deterministic Idempotency-Key goes with every attempt.
     That covers the one gap the database can't close: the provider accepted the
     message, then we crashed before committing.

  About the "Campaign audiences" entity from the brief: we don't add a separate
  table. The deliveries table is the audience snapshot at send time. Preview
  counts aren't stored; they're recomputed whenever needed.

  6. Audience segmentation design (D)

  DSL (v1)

  The design is typed predicates, not a free-form field/op/value triple.
  Behavioural conditions (events over a time window) are fundamentally different
  from attribute conditions, and typing them makes both validation and
  compilation simple.

  Shape:
  Rule      := { "match": "all"|"any", "conditions": [Condition…], "groups": 
  [Group…] }   // groups optional
  Group     := { "match": "all"|"any", "conditions": [Condition…] }             
            // depth ≤ 2, no nesting
  Condition := Attribute | Event | Behavior
  Attribute := { "type":"attribute", "field": F, "op": Op, "value": V }
  Event     := { "type":"event", "event":"cart_add"|"purchase",
                 "op":"exists"|"not_exists"|"count_gte"|"count_lte", "count"?: 
  int,
                 "within_days": 1..365, "category_in"?: [string] }
  Behavior  := { "type":"behavior", "predicate":"abandoned_cart", "within_days":
  1..365 }

  Field registry (the allow-list is the code; everything else is rejected):

  field: city
  type: enum (known cities)
  operators: eq, neq, in, not_in
  value rules: normalized with Turkish-aware folding; unknown city → error with
  a
  suggestion
  ────────────────────────────────────────
  field: country
  type: ISO-2
  operators: eq, in
  value rules:
  ────────────────────────────────────────
  field: gender
  type: enum
  operators: eq, in
  value rules:
  ────────────────────────────────────────
  field: age
  type: int (derived from birth_date)
  operators: gte, lte, between
  value rules: 13..120
  ────────────────────────────────────────
  field: signup_days_ago
  type: int
  operators: gte, lte, between
  value rules: 0..3650
  ────────────────────────────────────────
  field: last_active_days_ago
  type: int
  operators: gte, lte
  value rules: 0..3650
  ────────────────────────────────────────
  field: language
  type: enum
  operators: eq, in
  value rules:

  Limits: at most 10 conditions per group, 5 groups, 50 items in an in list, and
  the brief size is bounded.

  Consent is deliberately not in the DSL. The rule says who matches; whether we
  may reach them is decided by the backend. If the LLM emits anything
  consent-like, it's rejected with code consent_is_backend_enforced.

  Example Claude response for the example brief

  {
    "segment": {
      "match": "all",
      "conditions": [
        { "type": "attribute", "field": "city", "op": "eq", "value": "Istanbul"
  },
        { "type": "behavior", "predicate": "abandoned_cart", "within_days": 30 }
      ]
    },
    "suggested_channels": ["sms", "email"],
    "content_brief": {
      "goal": "cart_recovery",
      "tone": "friendly",
      "length": "short",
      "offer": { "kind": "percent_discount", "value": 30 }
    },
    "interpretation": "Users located in Istanbul who added at least one product 
  to their cart in the last 30 days and have not made a purchase since that cart
  addition.",
    "assumptions": [
      "\"Did not complete a purchase\" is interpreted as: no purchase after the 
  cart addition.",
      "No channel was specified, so both SMS and email are suggested."
    ],
    "unsupported": []
  }
  A brief like "users who love sneakers" would produce unsupported: 
  ["affinity/interest segmentation is not available"] instead of a made-up
  field.

  Validation pipeline

  1. Shape guaranteed at generation time. We send a JSON Schema through
     output_config.format (structured outputs), with enums for
     type/field/op/predicate. The DSL is deliberately shallow because
     structured-outputs schemas have limits (recursive $ref support needs to be
     checked on Day 3), and shallow rules are also easier for the marketer to
     read.
  2. Strict decode. A Go json.Decoder with DisallowUnknownFields. The type field
     picks the struct through a custom UnmarshalJSON. Unknown keys, a wrong
     discriminator or wrong types are rejected.
  3. Semantic validation (segment.Validate(rule) []ValidationError), driven by
     the registry:
     - field exists
     - operator is allowed for that field
     - value type and range are correct
     - count is present only for count_*
     - within_days is in range
     - list sizes and depth are within limits
     - city resolves to a known city
     - no contradictions where cheaply detectable (eq X and eq Y under all;
       becomes a warning)

     Errors are {path: "segment.conditions[1].op", code: "operator_not_allowed",
     message, allowed: [...]}. The same function validates LLM output, manual
     edits and PUT /segment, so there's one source of truth.
  4. Normalize (sort in lists, canonical city), then stamp "version": 1. Only
     the normalized rule is persisted.

  Translation to SQL

  segment.Compile(rule) (whereSQL string, args []any, err error):
  - Each registry entry has a hand-written fragment builder, for example city eq
    → u.city_normalized = $n. The builder adds the value to args and returns
    the placeholder.
  - Identifiers come only from Go constants; values are only ever bind 
    parameters. Nothing from the rule is ever concatenated into SQL text. A rule
    holding "Istanbul'; DROP TABLE users;--" just becomes a city value that
    fails validation, and even if it didn't, it would be a harmless parameter.
  - The behavioural predicates compile to EXISTS subqueries:

  -- abandoned_cart(within_days=$2) AND city=$1
  WITH matched AS (
    SELECT u.id
    FROM users u
    WHERE u.city_normalized = $1
      AND EXISTS (
        SELECT 1 FROM cart_events c
        WHERE c.user_id = u.id AND c.occurred_at >= now() - make_interval(days
  => $2)
          AND NOT EXISTS (SELECT 1 FROM purchases p
                          WHERE p.user_id = u.id AND p.purchased_at >=
  c.occurred_at))
  ),
  reach AS (
    SELECT m.id,
           (u.phone IS NOT NULL AND cs.status = 'opted_in') AS sms_ok,
           (u.email IS NOT NULL AND ce.status = 'opted_in') AS email_ok
    FROM matched m JOIN users u ON u.id = m.id
    LEFT JOIN channel_consents cs ON cs.user_id = m.id AND cs.channel = 'sms'
    LEFT JOIN channel_consents ce ON ce.user_id = m.id AND ce.channel = 'email'
  )
  SELECT count(*)                                AS matched,
         count(*) FILTER (WHERE sms_ok)          AS sms_reachable,
         count(*) FILTER (WHERE email_ok)        AS email_reachable,
         count(*) FILTER (WHERE sms_ok OR email_ok) AS any_reachable,
         count(*) FILTER (WHERE NOT sms_ok AND NOT email_ok) AS unreachable
  FROM reach;
  The query runs with SET LOCAL statement_timeout = '5s' inside a read-only
  transaction.

  Audience size and consent

  - Preview returns the counts above, the excluded counts per channel split into
    "no consent" and "no contact", and 5 masked sample users (Ayşe K., 
    İstanbul). That makes the rule concrete for the marketer.
  - Send reuses the reach CTE: INSERT INTO campaign_deliveries … SELECT … WHERE 
    sms_ok for SMS and likewise for email, snapshotting destination and
    variables, with ON CONFLICT DO NOTHING.
  - Dispatch checks consent again with one indexed lookup. If consent was
    revoked, the status becomes skipped_no_consent.

  7. Claude integration architecture (E)

  Layering

  // internal/llm — provider-neutral, tiny
  type Client interface {
      Complete(ctx context.Context, req Request) (Response, error)
      Stream(ctx context.Context, req Request, onText func(delta string) error)
  (Response, error)
  }
  type Request  struct { System string; Messages []Message; JSONSchema
  json.RawMessage; MaxTokens int; Effort string }
  type Response struct { Text string; StopReason StopReason; Usage Usage; Model
  string }
  // StopReason: EndTurn | MaxTokens | Refusal | Other

  // internal/ai — owns prompts, schemas, parsing, validation, repair
  type Interpreter struct { llm llm.Client; validator *segment.Validator; audit
  AuditRepo }
  func (i *Interpreter) Interpret(ctx, brief string) (InterpretResult, error)

  type Generator struct { llm llm.Client; validator *content.Validator; audit
  AuditRepo }
  func (g *Generator) Generate(ctx, in ContentInput, emit func(FieldDelta)
  error) (ContentDraft, error)
  Why the mock sits at llm.Client level and not at Interpreter level: a scripted
  mock client lets tests run the real prompt assembly, JSON parsing,
  validation, repair loop and stream extractor. Mocking the higher level would
  skip exactly the code we most need to test.

  Implementations:
  - llm.Anthropic:
    - Model from CLAUDE_MODEL, default claude-opus-5-5.
    - Structured outputs (output_config.format, JSON schema), never forced
      tool_choice, which is a 400 on this model.
    - effort: "low" for interpretation and "medium" for copy, both configurable.
    - Thinking left at its default; it can't be disabled on Opus 5.5.
    - Streaming through Messages.NewStreaming, forwarding text_deltas and
      accumulating the final message.
    - The SDK's built-in retries (2× on 429, 5xx and connection errors) are
      kept. option.WithRequestTimeout is set: 30 s for interpretation, 90 s for
      content.
    - stop_reason == "refusal" is checked before content is read. Server-side
      fallbacks: "default" can be turned on (I'd enable it; it's one config
      line).
    - The stable system prompt carries cache_control (cheap, helps repeated
      calls).
  - llm.Scripted (tests): a queue of canned responses and errors, plus chunked
    stream scripts. It can simulate: malformed JSON, truncation (MaxTokens),
    refusal, timeout, a stream dying mid-way, and chunks that split inside an
    escape sequence or a multi-byte UTF-8 rune.
  - llm.Demo (runtime without a key): deterministic and keyword-based.
    "istanbul", "cart", "30%" map to a plausible rule and content. It streams
    with artificial delay, so the UI is demonstrable. LLM_PROVIDER=auto picks
    Demo when ANTHROPIC_API_KEY is empty and logs a warning. The UI shows a
    "Mock AI" badge.

  Prompt design

  - Prompts are versioned files (prompts/segment_v1.tmpl), and their version is
    recorded in llm_calls.
  - System prompt for interpretation: the role; the field catalog generated from
    the registry (so the prompt can't drift from what the validator accepts);
    the operator semantics; the rules ("never invent fields, put anything you
    can't express in unsupported, state your interpretation choices in
    assumptions"); and 2–3 few-shot examples, including one with an unsupported
    request.
  - The brief goes inside <brief> tags, and the prompt says it is data. The
    marketer is trusted, but this habit makes injection boring.
  - The content prompt gets the content brief, the allowed variables, hard
    limits (SMS ≤ 150 to leave headroom, subject ≤ 70), the language (default:
    the brief's language), "plain text only, no links, no HTML", and an
    instruction to state the offer exactly as given.
  - No customer data is ever sent to the LLM.

  Handling malformed or incomplete output

  Situation: Transport 429/5xx/connection
  Handling: SDK retries (2×, backoff); then ErrLLMUnavailable → HTTP 503 with a
  retryable flag
  ────────────────────────────────────────
  Situation: stop_reason = max_tokens
  Handling: Treated as incomplete, never partially used; one retry with a higher

  max_tokens
  ────────────────────────────────────────
  Situation: stop_reason = refusal
  Handling: ErrLLMRefused with the category → UI: "AI declined; edit the brief
  or
  write manually"
  ────────────────────────────────────────
  Situation: JSON parse fails (unlikely with structured outputs, still handled)
  Handling: Counts as invalid → repair attempt
  ────────────────────────────────────────
  Situation: Valid JSON, semantic errors
  Handling: One repair turn: append the assistant output and a user message
  listing the structured validation errors (the history is only appended, never
   edited), then revalidate. A second failure returns the errors to the UI; the
   campaign stays editable through the form editor.
  ────────────────────────────────────────
  Situation: Stream interrupted
  Handling: The partial text is discarded and error is sent over SSE. Nothing is

  persisted.
  ────────────────────────────────────────
  Situation: Client disconnect
  Handling: The context is cancelled → the SDK stream is closed; recorded as
  cancelled

  Every attempt is written to llm_calls.

  Streaming content as structured JSON

  The model streams one JSON object,
  {"sms":"…","email_subject":"…","email_body":"…"}. ai/jsonstream.go is a small
  incremental extractor for a flat object of string fields. It tracks the
  current key and decodes string escapes and UTF-8 safely across chunk
  boundaries, and it emits FieldDelta{Field:"sms", Text:"Merhaba "} events. When
  the stream ends, the full text goes through the strict decoder and the
  validator; that final, validated result is authoritative. The UI shows deltas
  live and then replaces them with the validated version, plus any warnings.

  SSE events: meta (llm_call id, model) → delta (field, text)* → validated
  (content + errors/warnings + content_version) | error (code, message,
  retryable).

  8. Queue and delivery architecture (F)

  PostgreSQL vs Redis

  ┌─────────────────────┬──────────────┬────────────────────┬──────────────┐
  │                     │  Postgres    │  Redis (asynq /    │  River (Go   │
  │                     │    (SKIP     │      streams)      │ library on   │
  │                     │   LOCKED)    │                    │  Postgres)   │
  ├─────────────────────┼──────────────┼────────────────────┼──────────────┤
  │                     │              │ Redis service plus │              │
  │ New infrastructure  │ none         │  its persistence   │ none         │
  │                     │              │ configuration      │              │
  ├─────────────────────┼──────────────┼────────────────────┼──────────────┤
  │ Job enqueued        │              │                    │              │
  │ atomically with the │ yes, same    │ no; dual write →   │ yes          │
  │  business state     │ transaction  │ outbox needed      │              │
  │ change              │              │                    │              │
  ├─────────────────────┼──────────────┼────────────────────┼──────────────┤
  │ Source of truth for │ the job row  │ split between      │ separate     │
  │  delivery status    │ itself       │ Redis and Postgres │ jobs table + │
  │                     │              │                    │  our table   │
  ├─────────────────────┼──────────────┼────────────────────┼──────────────┤
  │ Throughput needed   │ trivially    │                    │              │
  │ (200/s)             │ within       │ overkill           │ fine         │
  │                     │ limits       │                    │              │
  ├─────────────────────┼──────────────┼────────────────────┼──────────────┤
  │ Shows understanding │              │                    │ low (hidden  │
  │  (case evaluation)  │ high         │ medium             │ in a         │
  │                     │              │                    │ library)     │
  └─────────────────────┴──────────────┴────────────────────┴──────────────┘

  Decision: a custom Postgres queue where the delivery row is the job. The
  decisive argument is atomicity: approve, enqueue and the status change happen
  in one transaction, so there's no outbox and no dual-write consistency bug.
  River is the best alternative and is noted in DECISIONS.md. We write our own
  because the queue is about 300 lines, it's where much of the evaluation weight
  sits, and it avoids having two status models (River's jobs plus our
  deliveries).

  Job lifecycle

  pending ──claim──▶ in_flight ──2xx──────────────▶ sent
     ▲                  │ ──429 / 5xx / timeout──▶ retry_scheduled 
  ──(next_attempt_at)──▶ claim again
     │                  │ ──4xx permanent────────▶ failed
     │                  │ ──attempts exhausted───▶ failed
     │                  │ ──no consent (recheck)─▶ skipped_no_consent
     └──lease expired (reaper)── in_flight with lease_until < now()  → 
  retry_scheduled (attempt logged 'lease_expired')

  Claim (batched, per channel):
  UPDATE campaign_deliveries d
  SET status='in_flight', lease_until = now() + interval '60 seconds',
  leased_by=$3,
      attempts = attempts + 1, updated_at = now()
  WHERE d.id IN (
    SELECT id FROM campaign_deliveries
    WHERE channel=$1 AND status IN ('pending','retry_scheduled') AND
  next_attempt_at <= now()
    ORDER BY next_attempt_at, id
    LIMIT $2
    FOR UPDATE SKIP LOCKED)
  RETURNING d.*;
  Completion is a guarded update: … WHERE id=$1 AND status='in_flight' AND 
  leased_by=$2. A worker whose lease was taken over can't overwrite the newer
  result.

  Worker concurrency and rate limiting

  - Shape: one worker process, with one dispatcher per channel. The dispatcher
    claims batches of about 50 and feeds a bounded pool of senders, about 25
    goroutines per channel. At 100/s with ~150 ms provider latency we need ≥15
    requests in flight.
  - Token bucket: rate.NewLimiter(100, burst=10) per channel. A sender calls
    limiter.Wait(ctx) before every HTTP attempt, retries included. Because the
    limit sits on the provider call, the 100/s ceiling holds whatever the queue
    looks like.
  - Adaptive pause on 429: the channel's limiter is paused until now + 
    Retry-After, using a shared "not before" timestamp per channel, so every
    sender backs off together instead of each one hitting the wall.
  - Multiple worker replicas: an in-process limiter is only correct with one 
    worker replica. That's the documented constraint, and Compose runs one. The
    upgrade path is either a per-replica rate of 100/N or a Postgres-backed
    token bucket (one row per channel, UPDATE … RETURNING).
  - Ordering: FIFO by next_attempt_at. A large campaign can delay a small one;
    acceptable, and noted.

  Retry strategy

  Provider result: 2xx
  Class: accepted
  Action: sent, store provider_message_id
  ────────────────────────────────────────
  Provider result: 409 / duplicate-idempotency response with the original id
  Class: accepted
  Action: sent (proves a previous attempt went through)
  ────────────────────────────────────────
  Provider result: 429
  Class: rate_limited
  Action: reschedule at max(Retry-After, backoff); channel pause; counts toward
  a
  separate cap (e.g. 10) so 429 storms don't burn the failure budget
  ────────────────────────────────────────
  Provider result: 5xx, connection reset, timeout (5 s client timeout)
  Class: transient
  Action: backoff and retry with the same idempotency key
  ────────────────────────────────────────
  Provider result: 400/404/422 (invalid number/email)
  Class: permanent
  Action: failed, no retry

  Backoff: min(cap, base · 2^(attempt-1)) with full jitter. Base 1 s, cap 60 s,
  at most 5 transient attempts. The policy is a pure function Next(attempt, 
  outcome, retryAfter) Decision, which makes it trivial to unit-test.

  Crashes and timeouts

  - Worker dies mid-send: the row stays in_flight until the lease expires (60 s,
    well above the 5 s HTTP timeout × in-process retries). Then the reaper, a
    10 s ticker in the worker, makes it claimable again.
  - Graceful shutdown (SIGTERM): stop claiming, let in-flight sends finish (with
    a deadline), and release unstarted leased rows back to pending.
  - Campaign completion: after each batch, UPDATE campaigns SET status = CASE 
    WHEN failed>0 THEN 'completed_with_failures' ELSE 'completed' END WHERE 
    id=$1 AND status='sending' AND NOT EXISTS (SELECT 1 FROM campaign_deliveries
    WHERE campaign_id=$1 AND status IN 
    ('pending','in_flight','retry_scheduled')).

  Delivery guarantees, stated honestly

  - Our system gives at-least-once delivery to the provider. No message is lost:
    every job reaches a terminal state, and leases plus the reaper recover from
    crashes.
  - Duplicates are blocked by construction up to the provider call (constraints,
    CAS, SKIP LOCKED, guarded completion).
  - One window remains. The provider accepts, then we crash, or the response
    times out, before committing sent. We will retry. That retry is a duplicate
    only if the provider ignores idempotency keys. Our mock provider honours
    them (a ledger keyed by Idempotency-Key that returns the original message
    id), so the result is effectively-once in this system, and we can prove it
    with the provider's ledger statistics.
  - We don't claim exactly-once. Exactly-once on the far side depends on the
    provider's dedupe guarantees, including how long it keeps keys, which we
    don't control in a real deployment.

  Mock provider

  - Endpoints: POST /v1/sms, POST /v1/email, each with an Idempotency-Key
    header.
  - Fault injection, configurable by env or POST /admin/faults:
    - latency distribution
    - transient 5xx rate
    - timeout rate (sleep beyond the client timeout, then commit: the nasty
      case)
    - permanent 4xx for numbers matching a pattern
    - its own 100/s limiter that returns 429 with Retry-After
  - Statistics: GET /admin/stats returns total requests, unique keys accepted,
    duplicate keys seen, and the maximum per-second rate observed per channel.
    Tests and the demo use these numbers to prove our delivery claims.

  Observability

  Prometheus metrics:
  - deliveries_total{channel,outcome}
  - provider_request_duration_seconds{channel}
  - provider_rate_limited_total
  - queue_depth{channel,status} (gauge, sampled every 5 s)
  - llm_requests_total{kind,status}
  - llm_latency_seconds
  - llm_tokens_total{direction}
  - segment_validation_errors_total{code}
  - http_requests_total{route,code}

  Logs are structured slog JSON with campaign_id / delivery_id. The worker
  writes a worker_heartbeats row, and the API's /readyz reports how stale it is.

  10. Frontend architecture (H)

  Pages
  - CampaignListPage: campaigns with status chips, and a "New campaign" button.
  - ComposerPage (/campaigns/:id/compose): a four-step stepper whose steps
    unlock according to the backend status (the frontend never decides).
    a. Brief: BriefInput (textarea, character counter, example prompts) →
       Interpret.
    b. Audience:
       - InterpretationCard: summary, with assumptions and unsupported items
         highlighted.
       - SegmentRuleView: the rule as human-readable chips, e.g. "City is
         İstanbul", "Abandoned cart in the last 30 days".
       - SegmentRuleEditor: an optional form built from a /meta/segment-fields
         endpoint that exposes the registry.
       - AudienceCard: matched/reachable per channel, excluded reasons, sample,
         channel checkboxes.
    c. Content:
       - ContentStreamPanel: Generate/Regenerate, live text per field, a "Mock
         AI" badge.
       - SmsEditor + SmsPreview (phone frame, worst-case count,
         encoding/segments).
       - EmailEditor + EmailPreview (sandboxed iframe with escaped text plus the
         backend footer).
       - A recipient switcher to preview with a real sample user.
       - ValidationList (server errors and warnings).
    d. Review & approve: ApprovalDialog summarizes audience counts per channel,
       the final rendered content and the versions, and needs an explicit
       confirmation (checkbox plus button). Send is a separate, clearly labelled
       action after approval.
  - CampaignDashboardPage: ChannelProgress (a stacked bar per channel),
    StatTiles, the live rate, FailureTable (paged from
    /deliveries?status=failed), and a ConnectionBadge (live / reconnecting).

  How specific concerns are handled
  - Streaming AI: useContentStream() uses fetch + ReadableStream + TextDecoder
    with a small SSE frame parser. It exposes reactive fields, status, error and
    abort(). An AbortController cancels the stream on unmount or regenerate.
  - Live dashboard: useCampaignEvents(id) wraps EventSource (built-in reconnect,
    with exponential backoff on top), replaces state on each snapshot, and
    closes once the campaign reaches a terminal state.
  - Editing: a local draft with a debounced server preview/validate call.
    Client-side counters are for UX only and the server is authoritative. While
    an edit is unsaved, approval is disabled.
  - Safety: no v-html anywhere for AI content. {{variables}} are highlighted
    with tokenized spans, not HTML injection.
  - State: server state is fetched per page. One Pinia store holds the active
    composer campaign and its version, for optimistic concurrency.

  13. Initial DECISIONS.md content (K)

  ADR-001: Modular monolith with separate api/worker processes
  - Context: a 7-day timeline, one team, but distinct runtime profiles
    (interactive vs. background).
  - Alternatives: a single process; microservices.
  - Decision: one Go module and one image with api, worker and mockprovider
    entrypoints, organized by feature (segment, content, ai, delivery,
    campaign).
  - Reasoning: isolated failures and resources without the cost of distributed
    systems; shared domain code.
  - Trade-offs: module boundaries are enforced by convention, not deployment;
    scaling is per process, not per feature.

  ADR-002: PostgreSQL job queue; the delivery row is the job
  - Context: we need reliable async delivery, and the brief says to evaluate
    Postgres before Redis.
  - Alternatives: Redis + asynq; River; a separate generic jobs table.
  - Decision: campaign_deliveries with FOR UPDATE SKIP LOCKED claims, leases and
    a reaper.
  - Reasoning: enqueue is atomic with the approve→sending transition (no outbox
    or dual writes); one source of truth for status; no new infrastructure; more
    than enough for 200 msg/s.
  - Trade-offs: polling latency (~250 ms idle poll); write load on Postgres at
    much larger scale; we own ~300 lines of queue code. River is the natural
    migration.

  ADR-003: At-least-once delivery with deterministic idempotency keys
  - Context: "never send twice" and crash tolerance.
  - Alternatives: at-most-once (mark sent before calling: loses messages on
    crash); claiming exactly-once.
  - Decision: layered dedupe (unique constraint, CAS send, SKIP LOCKED, guarded
    completion) plus key campaign:user:channel on every attempt.
  - Reasoning: this is the strongest guarantee you can actually achieve against
    an external provider.
  - Trade-offs: effectively-once depends on the provider honouring keys;
    documented, and demonstrated with the mock provider's ledger.

  ADR-004: A typed segmentation DSL compiled through a registry; the LLM never 
  writes SQL
  - Context: LLM output is untrusted, and the requirement forbids running
    generated SQL.
  - Alternatives: LLM-generated SQL plus a parser or sandbox; a generic
    field/op/value JSON.
  - Decision: typed predicates (attribute/event/behavior), a shallow structure,
    a registry-driven validator, parameterized fragment builders.
  - Reasoning: the attack surface is the allow-list; one validator for AI and
    human input; the prompt is generated from the registry, so it can't drift.
  - Trade-offs: less expressive; each new segmentation capability needs code
    (intentionally).

  ADR-005: Consent enforced by the backend, outside the DSL, re-checked at 
  dispatch
  - Decision and reasoning: a legal and business invariant must not depend on
    the LLM. A missing consent row means no consent.
  - Trade-off: an extra lookup per send (negligible).

  ADR-006: Structured outputs, then strict decode, then semantic validation, 
  with one repair attempt
  - Alternatives: prompt-only JSON plus regex extraction; forced tool use (not
    supported on the chosen model); unlimited retries.
  - Reasoning: the schema removes most syntax failures; semantic validation is
    still needed; one repair limits cost and latency, then the human takes over.
  - Trade-offs: the schema has to be shallow (structured-outputs limits);
    occasional extra latency from a repair.

  ADR-007: LLM abstraction at client level; scripted and demo mocks
  - Reasoning: tests run the real prompt, parse, validate and repair code; the
    app runs without a key.
  - Trade-off: the mocks don't capture the model's real quality; a live smoke
    test is optional.

  ADR-008: The official Anthropic Go SDK
  - Reasoning: maintained; typed streaming; retries for 429, 5xx and connection
    errors; reads the key from the environment.
  - Trade-off: we're coupled to SDK types (contained inside llm/anthropic.go).

  ADR-009: Model claude-opus-5-5 by default, configurable through CLAUDE_MODEL, 
  effort tuned per call
  - Trade-off: cost vs quality. Interpretation runs at low effort, and the model
    can be swapped without code changes.

  ADR-010: SSE for both streams; fetch-stream for POST generation; snapshot 
  events for status
  - Alternatives: WebSockets; client polling.
  - Reasoning: traffic only goes one way; works through the nginx proxy;
    reconnecting to snapshot events is trivial.
  - Trade-off: generation can't be resumed after a disconnect (by design:
    regenerate).

  ADR-011: Status stream from DB polling (1 s), not LISTEN/NOTIFY
  - Reasoning: correct with multiple API instances, no missed notifications,
    cheap at this scale.
  - Trade-off: up to 1 s latency, and a query per open stream per second.

  ADR-012: In-process token bucket per channel; single worker replica
  - Reasoning: simple and exact for one process; respects 100/s for every
    attempt, retries included; 429 pauses the whole channel.
  - Trade-off: horizontal scaling needs a distributed limiter (documented
    upgrade path).

  ADR-013: Custom {{var}} templating with worst-case length validation
  - Alternatives: text/template; mustache libraries.
  - Reasoning: with text/template, LLM-written text could run template actions;
    we need an allow-list of variables and length calculation anyway.
  - Trade-off: no conditionals or loops (not needed).

  ADR-014: Approval bound to the content version and segment version; any edit 
  un-approves; audience snapshot at send
  - Reasoning: what was approved is exactly what gets sent.
  - Trade-off: re-approval friction after small edits; the audience may drift
    between estimate and send (shown explicitly).

  ADR-015: pgx with handwritten SQL, stdlib router, no ORM
  - Reasoning: the case is about SQL correctness, and the compiler emits SQL
    anyway; minimal dependencies.
  - Trade-off: more boilerplate in the repositories.

  ADR-016: Mock provider as a separate HTTP service with fault injection and a 
  dedupe ledger
  - Reasoning: realistic 429, timeout and idempotency behaviour; gives outside
    proof of the delivery guarantees.
  - Trade-off: one more container.

  1. Revised high-level architecture

  The components are unchanged: one Go module with api, worker, mockprovider and
  seed entrypoints, PostgreSQL as the only infrastructure, and nginx serving
  Vue. What changed is the campaign lifecycle and where the audience gets
  frozen:

   draft ─interpret─▶ segmented ─generate/edit─▶ content_ready ─prepare─▶ 
  pending_approval ─confirm─▶ approved ─send─▶ sending ─▶ completed
     ▲                  ▲  (edit rule)               ▲  (edit content/channels) 
    │                  │                    └▶ completed_with_failures
     └──────────────────┴────────────────────────────┴────── any edit: approval 
  superseded, held rows deleted ─┘

   prepare  = compute audience from the frozen rule → INSERT held delivery rows 
  + campaign_approvals(status=pending)
   confirm  = marketer has seen THOSE exact counts/content → 
  approval.status=approved (CAS)
   send     = CAS campaign approved→sending + UPDATE deliveries held→pending 
  WHERE approval_id = X
   dispatch = worker claims pending rows of an approved+sending approval → 
  re-checks consent and contact → provider

  Module boundaries stay as before (segment, content, ai, llm, campaign,
  delivery, provider, platform, httpapi). The changes:
  - New approval package, holding the prepare/confirm/revoke logic and the
    snapshot query.
  - delivery gains ratelimit.SlidingWindow and loses its enqueue logic.
  - Delivery rows are inserted in exactly one place, approval.Prepare. That
    single insert point is what enforces the invariant in code.

  2. Revised database model: approval and snapshot

  Options I evaluated

  Option: A. campaign_audience_snapshots + snapshot_members, copied into 
  deliveries at send
  Pros: Clear meaning ("who was approved" separate from "what happened")
  Cons: Every row exists twice; the copy step is one more place for the two to
  drift; two uniqueness rules to keep in step
  ────────────────────────────────────────
  Option: B. Snapshot stored as a JSONB/array of user ids on the approval
  Pros: One row
  Cons: Can't join or index it; destinations and variables have to be resolved
  again at send; awkward for a few thousand ids
  ────────────────────────────────────────
  Option: C. campaign_approvals + delivery rows created as held (chosen)
  Pros: One row per (user, channel) for its whole life; the uniqueness
  constraint
  already covers it; send is one UPDATE; stats are one GROUP BY
  Cons: The queue table holds rows that aren't authorized yet. Mitigated: the
  claim query only selects pending/retry_scheduled and joins to an approved,
  sending approval.

  C is the simplest design that keeps the invariant, so I chose it.

  Schema (users, consents, cart, purchases and contents are unchanged from v1)

  CREATE TABLE campaign_approvals (
    id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    campaign_id       UUID NOT NULL REFERENCES campaigns(id),
    status            TEXT NOT NULL CHECK (status IN
  ('pending','approved','superseded','expired','consumed')),
    segment_version   INT  NOT NULL,
    segment_rule      JSONB NOT NULL,            -- frozen copy of the validated
  rule
    content_id        BIGINT NOT NULL REFERENCES campaign_contents(id),  -- 
  immutable version

    audience_stats    JSONB NOT NULL,            -- the exact partition shown to
  the marketer (§5)

  (asserted in the same transaction)
    snapshot_digest   TEXT NOT NULL,             -- sha256 of sorted 
  (user_id,channel), for audit

  );

  Transactions

  - Prepare (POST /campaigns/{id}/approvals), all in one transaction:
    a. Lock the campaign row.
    b. Require status content_ready and a valid current content version.
    c. Mark any earlier pending approval superseded and delete its held rows.
       They were never sendable, and the approval row keeps the record.
    d. Run the compiled audience query for the selected channels.
    e. Insert eligible rows as held with frozen vars.
    f. Compute the statistics and digest, insert the approval as pending, and
       set campaign status pending_approval.

    Returns the approval id, the counts, a sample, the rendered content and
    expires_at.
  - Confirm (POST /approvals/{aid}/confirm, body repeats segment_version,
    content_version, channels): a compare-and-set that only succeeds while the
    approval is pending and unexpired, the versions and channels match, and the
    campaign is still pending_approval. Approval status becomes approved, and
    the campaign becomes approved. The approval is bound to the segment version,
    content version, channels and snapshot together, because all four live on
    the approval row.
  - Send: a compare-and-set takes the campaign from approved to sending and the
    approval from approved (unexpired) to consumed, then UPDATE 
    campaign_deliveries SET status='pending' WHERE approval_id=$1 AND 
    status='held'. The number of rows updated must equal snapshot_count, or the
    transaction rolls back.
  - Claim: joins campaign_approvals a ON a.id = d.approval_id AND 
    a.status='consumed' and campaigns c ON c.status='sending'. This is defense
    in depth on top of the status filter.

  Invariant: never send to anyone outside the approved snapshot

  - No code path inserts delivery rows except Prepare, and every row carries a
    non-null approval_id foreign key.
  - Send only changes the status of existing rows; it never runs the audience
    query.
  - Users who start matching the rule after prepare are not in the snapshot, so
    they are never sent to.
  - Test: prepare and confirm, insert 50 new matching users, send. The provider
    ledger contains only the snapshot's user ids.

  Consent and contact changes between approval and dispatch

  Consent and contact are rechecked at dispatch, one indexed lookup per claimed
  batch:

  ┌──────────────────┬──────────────────────────────────────────────────────┐
  │  Change after    │                      Behaviour                       │
  │     approval     │                                                      │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ Consent revoked  │ skipped_consent_revoked, never sent, counted         │
  │ for that channel │ separately                                           │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ Consent newly    │                                                      │
  │ granted / new    │ Not added; the snapshot is closed                    │
  │ user matches     │                                                      │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │ Contact removed  │ skipped_no_contact                                   │
  ├──────────────────┼──────────────────────────────────────────────────────┤
  │                  │ Send to the current address, recorded on first       │
  │ Contact changed  │ dispatch and kept fixed for retries so the           │
  │                  │ idempotency key always points to one destination     │
  └──────────────────┴──────────────────────────────────────────────────────┘

  - Why variables are frozen but addresses are not: personalization is part of
    what was approved. Routing has to follow the user's latest data, because
    sending to an address the user has since removed is the worse failure.
  - Staleness I'm not solving in core: a user who purchased after approval still
    gets the abandoned-cart message. Approval expiry bounds this (24 h
    default). Re-checking the rule at dispatch is a stretch item, and it can
    only ever remove recipients, never add them.

  3. Revised rate-limiting design

  What each limiter actually allows

  The strictest reading of "max 100 per second" is at most 100 requests in any 
  rolling 1-second interval. Meeting it also satisfies the weaker
  calendar-second reading.

  ┌──────────────────────┬────────────────────────┬────────────────────────┐
  │       Limiter        │    Worst case in a     │        Verdict         │
  │                      │      rolling 1 s       │                        │
  ├──────────────────────┼────────────────────────┼────────────────────────┤
  │ Token bucket (100/s, │ 110                    │ ❌ fails               │
  │  burst 10)           │                        │                        │
  ├──────────────────────┼────────────────────────┼────────────────────────┤
  │ Token bucket (100/s, │ 101 in a closed        │ Borderline; depends on │
  │  burst 1)            │ interval [t, t+1s];    │  interval semantics,   │
  │                      │ 100 half-open          │ hard to explain        │
  ├──────────────────────┼────────────────────────┼────────────────────────┤
  │ Fixed window (100    │ 200 (100 at the end of │ ❌ fails the rolling   │
  │ per calendar second) │  one second, 100 at    │ reading                │
  │                      │ the start of the next) │                        │
  ├──────────────────────┼────────────────────────┼────────────────────────┤
  │ Sliding-window log   │ 100, exactly           │ ✅ chosen              │
  └──────────────────────┴────────────────────────┴────────────────────────┘

  Design: sliding-window log, one per channel

  - State: a ring buffer of the last N=100 acquire times per channel, a mutex, a
    pausedUntil time, and an injected clock.
  - Acquire(ctx):
    a. Lock.
    b. Compute wait = max(pausedUntil, oldest + W) - now, where oldest is the
       acquire time N entries back.
    c. If wait ≤ 0, record now into the ring, unlock and return.
    d. Otherwise unlock, sleep for wait (or until ctx is done) and go back to
       step 1.
  - Why it works: "the 100th-previous request is at least W old" is exactly "at
    most 100 in any window of length W". It's about 40 lines, deterministic with
    a fake clock, and has no dependencies.
  - SMS and email each get their own instance. Nothing is shared.
  - Every HTTP attempt calls Acquire, retries included, and so do attempts that
    later fail at the connection level. Counting those is conservative; we never
    undercount.
  - 429 pause: Pause(until) sets pausedUntil = max(pausedUntil, now + 
    RetryAfter). Retry-After is parsed as seconds or as an HTTP date; it
    defaults to 1 s when missing and is capped at 30 s. Requests already in
    flight finish; new acquires wait. The delivery that got the 429 goes to
    retry_scheduled with next_attempt_at = now + RetryAfter. 429s have their own
    counter (cap 10), so they don't use up the 5 transient-error retries.

  Gap the feedback didn't raise: our rate is not the provider's rate

  The limiter controls when requests start. The provider counts when they
  arrive. Network and scheduling jitter can squeeze two starts that are 1,000 ms
  apart into arrivals 990 ms apart, giving 101 arrivals in a rolling second. So
  the window is W = 1s + margin. The margin defaults to 25 ms (config
  RATE_WINDOW_MARGIN), which is far above the jitter of a local Docker network
  and costs about 2.5% of throughput. It's documented as a deliberate safety
  margin.

  Verification

  - Unit test (fake clock): 1,000 acquires from 30 goroutines. Over the recorded
    times, the maximum in any rolling window W is ≤100. Pause blocks until
    pausedUntil.
  - Integration test (real time, ~10 s):
    - The mock provider records arrival times per channel and exposes
      max_requests_in_any_rolling_1s (sorted times, two-pointer scan) at
      /admin/stats.
    - Setup: 1,500 messages per channel, 5% injected 5xx and 2% 429.
    - Assertions: maximum ≤100 for each channel separately; both channels reach
      about 95–100/s at the same time (proving the limits are independent); and
      after a 429, no request arrives on that channel before the Retry-After
      deadline.

  Distributed rate limiting is out of scope: one worker replica, stated as an
  explicit constraint.

  4. Revised SMS validation design

  Content is normalized to Unicode NFC when saved, because a decomposed "ş"
  counts as 2 code points. After that, each measure has a defined role:

  Measure: Character count
  Definition: Unicode code points (runes), after NFC
  Role: Hard limit: SMS ≤160, subject ≤80, email body ≤5,000. Runes are never
  fewer than visible characters, so the check is conservative.
  ────────────────────────────────────────
  Measure: Worst-case personalized length
  Definition: Template length with each {{var}} replaced by its declared maximum
   
  length; a fallback ({{first_name|there}}) counts max(declared, 
  len(fallback))
  Role: The hard limit is applied to this value, while editing, at approval and
  before every render
  ────────────────────────────────────────
  Measure: Encoding
  Definition: GSM-7 if every character is in the GSM 03.38 basic set or
  extension
  table (extension characters ^{}\[~]|€ count as 2 septets); otherwise UCS-2
  Role: Warning only. Turkish ğ, ş, ı, İ force UCS-2. We don't implement the
  Turkish national shift table.
  ────────────────────────────────────────
  Measure: Segments
  Definition: GSM-7: ≤160 → 1, else ⌈septets/153⌉. UCS-2: ≤70 UTF-16 units → 1,
  else ⌈units/67⌉
  Role: Warning only ("3 SMS segments, billed ×3")

  Worst-case calculation

  - The variable registry is code: first_name: max 20, last_name: max 25, city: 
    max = longest name in the known-cities list (computed at startup).
  - The data enforces the same maximums: CHECK (char_length(first_name) <= 20)
    and so on, plus the seed respects them. That's what makes the declared
    maximum a real upper bound, not a guess.
  - Unknown or malformed variables are blocking errors.
  - Defense in depth: the renderer asserts the actual rendered length. If it
    were ever exceeded, which can't happen given the CHECK constraints, the
    delivery fails with content_too_long and a metric is incremented. It is
    never silently truncated.
  - One validator for everything: AI output, edits and the approval check all
    use content.Validate. It returns {errors[], warnings[], sms: 
    {chars_worst_case, encoding, segments_worst_case}}.

  5. Corrected audience statistics

  The rule: for each selected channel, every matched user falls into exactly one
  category, checked in this order:

  1. no_contact: no phone (SMS) or no email address (email). Consent doesn't
     matter when there's nowhere to send.
  2. no_consent: has contact, but the consent row is missing or opted_out.
  3. eligible: has contact and is opted_in.

  So matched = no_contact + no_consent + eligible holds per channel, by
  construction.

  Across channels, users are also partitioned: eligible_both + sms_only + 
  email_only + unreachable = matched.

  Units are labelled: users and messages are never added together.
  "audience": {
    "matched_users": 412,
    "by_channel": {
      "sms":   { "eligible": 251, "no_consent": 140, "no_contact": 21 },
      "email": { "eligible": 318, "no_consent":  82, "no_contact": 12 }
    },
    "reach_users": { "both": 202, "sms_only": 49, "email_only": 116,
  "unreachable": 45 },
    "messages_to_send": 569
  }
  Checks: 251+140+21 = 412, 318+82+12 = 412, 202+49+116+45 = 412, and 251+318 =
  569. These identities are asserted in tests. One SQL query computes them with
  CASE expressions per channel and count(*) FILTER (...). Unselected channels
  are left out of by_channel and messages_to_send.

  Independent metrics (for example "users missing consent, regardless of
  contact") overlap with the categories above. They're left out on purpose:
  they're what caused the double-counting.

  Delivery statistics follow the same principle. Each snapshot row has exactly
  one status, so for each channel approved_total = held + pending + in_flight + 
  retry_scheduled + sent + failed + skipped_consent_revoked + skipped_no_contact
  + cancelled. The dashboard shows approved_total, which is constant, as the
  denominator.

  6. Final Anthropic SDK and model strategy

  SDK, checked against the official Go SDK docs and changelog

  Item: Module
  Decision: github.com/anthropics/anthropic-sdk-go/v2, pinned to v2.5.0
  (released
  2026-11-02; latest at time of writing) in go.mod, verified by go.sum
  ────────────────────────────────────────
  Item: Go
  Decision: 1.25+ (required by SDK v2); we use Go 1.25 in Docker
  ────────────────────────────────────────
  Item: API version
  Decision: v2 sends anthropic-version: 2026-10-21. temperature/top_p/top_k are
  rejected there, so we never send sampling parameters. Older v1-path examples
  (including the ones in my first proposal) are out of date.
  ────────────────────────────────────────
  Item: API key
  Decision: anthropic.NewClient() reads ANTHROPIC_API_KEY by default. We pass
  option.WithAPIKey(cfg.APIKey) explicitly from our config, so a missing key is
   detected at startup and the app falls back to the mock in LLM_PROVIDER=auto.
   The key is never logged.
  ────────────────────────────────────────
  Item: Streaming
  Decision: client.Messages.NewStreaming(ctx, params). For each event:
  message.Accumulate(event) (returns an error), then switch on event.AsAny().
  ContentBlockDeltaEvent → TextDelta gives the deltas, which feed the JSON
  field extractor. Thinking-block start events become an SSE status: thinking
  event, because Opus 5.5 thinks before writing, so the first text arrives
  late. stream.Err() is checked at the end.
  ────────────────────────────────────────
  Item: Structured output
  Decision: Stable API: OutputConfig: anthropic.OutputConfigParam{Format: 
  anthropic.JSONOutputFormatParam{Schema: <map[string]any>}, Effort: …} on
  MessageNewParams. The result arrives as a text block, which we decode
  strictly ourselves. We use the raw-map form because passing a Go struct as
  the schema is beta-only. The schema is generated deterministically from the
  field registry, so the compiled grammar stays cached (24 h).
  ────────────────────────────────────────
  Item: Schema limits
  Decision: Supported: enum, const, anyOf, $ref/$defs, additionalProperties: 
  false. Not supported: recursive schemas, minLength/maxLength,
  minimum/maximum. So the schema enforces shape and enums, and the Go 
  validator enforces every length and range. This confirms the shallow DSL.
  ────────────────────────────────────────
  Item: Retries
  Decision: The SDK retries connection errors, 408, 409, 429 and ≥500 2 times by
   
  default with exponential backoff. Set through option.WithMaxRetries(n)
  (config CLAUDE_MAX_RETRIES, default 2). The total deadline comes from
  context.WithTimeout; the per-attempt limit from option.WithRequestTimeout.
  Our own layer adds only one repair turn for semantic failures.
  ────────────────────────────────────────
  Item: Errors
  Decision: errors.As(err, &apierr *anthropic.Error) gives StatusCode and
  RequestID, which we log. Transport errors come back unwrapped (*url.Error).
  We map them to ErrLLMUnavailable (retryable), ErrLLMRejected (400),
  ErrLLMRefused (stop_reason == refusal; output may not match the schema) and
  ErrLLMTruncated (max_tokens).
  ────────────────────────────────────────
  Item: Model-specific constraints (Opus 5.5)
  Decision: Thinking is always on (we control effort); forced tool_choice
  returns
  400; no prefill. Structured outputs avoid all three.

  Model selection is per task, set by env, never hardcoded

  LLM_PROVIDER=auto|anthropic|mock
  CLAUDE_SEGMENT_MODEL=claude-opus-5-5     CLAUDE_SEGMENT_EFFORT=low     
  CLAUDE_SEGMENT_TIMEOUT=45s
  CLAUDE_CONTENT_MODEL=claude-opus-5-5     CLAUDE_CONTENT_EFFORT=medium  
  CLAUDE_CONTENT_TIMEOUT=90s
  The model is a string in config, passed down through llm.Request.Model, and
  recorded with each AI-produced segment and content version. No SDK model
  constants appear in the code.

  Model comparison

  Interpretation (~2.5k input, ~0.4k JSON output, schema-constrained)
  Claude Opus 5.5 ($4 / $20 per MTok): Best at handling ambiguity (choosing
  abandoned_cart vs. "no purchase in window", writing useful
  assumptions/unsupported). Thinking is always on, so expect a few seconds even
   at low. ≈ $0.02–0.05 per call.
  Claude Sonnet 5.5 ($2 / $10 per MTok): Structured outputs guarantee the shape,

  so what's left is the semantic choice. Very likely good enough. Thinking can
  be turned off (between_tools), so latency is lower. About half the cost.
  ────────────────────────────────────────
  Content (streamed, Turkish/English copy, tight length limits)
  Claude Opus 5.5 ($4 / $20 per MTok): Noticeably better at tone and fitting
  copy
  into tight limits; fewer repair turns. Thinking delays the first token.
  Claude Sonnet 5.5 ($2 / $10 per MTok): Good copy, faster first token. May need

  the repair turn more often for length.

  Recommendation:
  - Default both tasks to claude-opus-5-5 (interpretation at low effort, content
    at medium). You've prioritized quality and predictable structured output,
    and at demo volumes the cost difference is a few cents per campaign.
  - Measure, don't guess. Add a 12-brief mini evaluation on Day 2 (make 
    eval-segment MODEL=…): an exact match on the normalized rule, plus a latency
    report.
  - If Sonnet 5.5 matches Opus on interpretation, switching is a one-line env
    change, and it's your decision.
  - Haiku 5.5 is not recommended as the default: it's the riskiest on ambiguity,
    and refusals have no server-side fallback.
  - Refusal fallback: Anthropic recommends fallbacks: "default" for Opus 5.5. In
    Go it needs the beta Messages API (client.Beta.Messages), which is a second
    code path. I classed it as B, behind CLAUDE_REFUSAL_FALLBACK. A refusal is
    unlikely for marketing copy, and core handles it explicitly in the UI.

  9. Final architectural decisions for DECISIONS.md

  1. Modular monolith with separate api/worker/mockprovider processes.
     (unchanged)
  2. PostgreSQL queue where the delivery row is the job. SKIP LOCKED, leases,
     reaper; River noted as the alternative. (unchanged)
  3. At-least-once delivery + deterministic idempotency keys. Effectively-once
     only when the provider honours keys; we don't claim exactly-once. (key now 
     includes approval_id)
  4. Typed shallow DSL, registry-compiled to parameterized SQL. The LLM never
     writes SQL. (now also justified by the structured-outputs limits: no 
     recursion, no length or range keywords)
  5. Approval bound to a prepared snapshot (new): prepare/confirm;
     campaign_approvals + held delivery rows instead of a separate snapshot
     table. One insert path; send only changes statuses.
  6. Consent and contact rechecked at dispatch; personalization frozen at 
     approval (new). The snapshot can only shrink, never grow.
  7. Sliding-window-log limiter per channel with a timing margin (new; replaces 
     the token bucket). Every attempt counts; 429 pauses the channel; checked
     against the rate the provider observes; single worker replica by design.
  8. SMS limit is the worst-case rune count after NFC. Declared variable
     maximums enforced by DB constraints; encoding and segments are warnings.
     (new)
  9. Audience statistics as an ordered, mutually exclusive partition (no contact
     → no consent → eligible), with users and messages in separate units. (new)
  10. Anthropic Go SDK v2 (/v2, Go 1.25, API 2026-10-21); stable structured
      outputs with a raw schema; SDK retries kept; one semantic repair turn.
      (revised)
  11. Model and effort configured per task by env; Opus 5.5 by default, Sonnet
      5.5 as the measured alternative. (new)
  12. LLM abstraction at the client level; scripted mock for tests, keyword demo
      mock for running without a key. (unchanged)
  13. SSE: fetch-stream for generation, EventSource with snapshot events for
      status; polling the DB instead of LISTEN/NOTIFY. (unchanged)
  14. Custom {{var}} templating, not text/template. (unchanged)
  15. pgx with handwritten SQL, stdlib router, no ORM. (unchanged)
  16. Mock provider as an HTTP service with fault injection, idempotency ledger
      and rolling-rate statistics. (extended)
  17. Scope tiers (A/B/C), with what's explicitly out of scope and why. (new)

  Each entry gets the Context / Alternatives / Decision / Reasoning / Trade-offs
  format. The content for each is in this document and the previous one.

  Your five concerns

  A. Consent revocation race. For each provider request the order is: take a
  rate-limit slot, run one short database statement (the "precheck"), then send
  the request immediately. The precheck confirms the worker still owns the row,
  the campaign is still sending, the user still has consent and a contact
  address, and it saves the destination.
  - What we guarantee: if a revocation commits before the precheck starts, it's
    honoured. That attempt and every later attempt are not sent.
  - What we don't: if the revocation commits after the precheck but before the
    provider receives the request, that one attempt still goes out. The window
    is about 20 ms plus network transit, and the 5 s request timeout caps it.
  - Why no lock: holding a lock on the consent row during the HTTP request would
    only make the revocation commit after the send. The message would still go
    out, and we'd have tied up connections and blocked consent changes for
    nothing.
  - Why the check comes after the rate-limit wait: checking at claim time
    instead would widen the window to include rate-limit waits and 429 pauses.

  B. Approval expiry and state transitions.
  - Approval statuses are pending, approved, consumed, revoked (with a reason)
    and expired.
  - Every campaign and approval transition locks the campaign row first, so a
    send racing an expiry is resolved one at a time.
  - Confirm and send succeed only if the approval hasn't expired at that moment,
    so correctness doesn't depend on the background expiry job having run.
  - Revoking or expiring an approval deletes its held rows and resets the
    campaign status in the same transaction.
  - Deliveries can only be claimed from the consumed approval of a campaign that
    is sending. A consumed approval never expires.

  C. Idempotency and destination consistency.
  - The idempotency key changed from the previous round to
    campaign_id:user_id:channel. It now matches the business rule "one message
    per recipient per channel", so even a bug that created a second row would
    collide at the provider.
  - The destination is saved before the first request and never changes. Every
    retry sends exactly the same key, address and body.
  - If the provider accepted a message but the worker crashed before recording 
    it: the lease expires, an "unknown" attempt is logged, and the retry gets
    the original message id back from the provider, so the row becomes sent and
    only one message went out. If consent was revoked in the meantime, the row
    ends skipped_consent_revoked and is flagged outcome_uncertain.
  - What we claim: at-least-once requests to the provider. That becomes at most
    one delivered message per recipient and channel only if the provider honours
    idempotency keys. We do not claim exactly-once.

  D. Rate limiter.
  - Each channel keeps a log of its last 100 request times. A new request may
    start only once the 100th-most-recent one is at least 1 s plus a margin old.
    The check and the record happen under one lock, so concurrent goroutines
    can't slip past it.
  - Every provider request goes through one function that takes a slot first, so
    retries count.
  - A 429 pauses only that channel's limiter.
  - The gap between taking a slot and sending is capped at 20 ms, so the 50 ms
    default margin covers that gap plus up to 30 ms of network jitter. The
    margin is configurable.
  - The integration test records arrival times inside the mock provider. It
    asserts at most 100 per channel in any rolling second, that arrivals equal
    our recorded attempts, and that a 429 pauses only its own channel.

  - ARCHITECTURE §5.1 has a new paragraph on expiry time semantics. Every

  - Expiry comparisons use clock_timestamp(), never now(), CURRENT_TIMESTAMP or
    a time computed in Go.
  - The timestamps that define expiry (prepared_at, approved_at, expires_at,
    consumed_at) are also set from clock_timestamp() after the lock. prepared_at
    no longer has DEFAULT now().
  - The approval diagram, the Prepare/Confirm/Expire/Send rows in §5.5 and the
    expiry mechanism in §5.3 now follow this. The sweeper finds candidates
    without locking, then for each one locks the campaign row and checks again
    with clock_timestamp().
  - ADR-006 is rewritten to say why now() and Go-side timestamps were rejected.
    CLAUDE.md's coding convention and invariant 8 are updated, and a prohibited
    shortcut is added.

  Provider idempotency (correction 2)
  - §10.6: each provider adapter declares provider.Capabilities{IdempotencyKeys,
    KeyRetention}. The mock declares true, kept for the life of the process.
  - The worker works out the retry horizon H from configuration at startup:
    about 12 minutes with defaults. The old "≈10 min" figure was too low.
  - The worker logs the resulting guarantee at startup and reports it in
    /readyz.
  - §10.9 and ADR-009 now claim at most one delivered message per recipient and
    channel only for a provider whose key retention is at least H. For any other

  - The crash walkthrough in §10.7 now states the duplicate case for a provider
    without idempotency.
  - Invariant 18 and ADR-020 are updated, and a prohibited shortcut is added.

  - §10.2 now has a precheck budget, DISPATCH_MAX_PRECHECK=15ms, enforced as a
    deadline on the precheck query.
  - A final gate is the last statement before http.Client.Do: if more than
    DISPATCH_MAX_SLOT_TO_REQUEST=20ms has passed since the slot was granted, the
    request is aborted.
  - A table covers the three cases you listed (precheck too slow, total time too

  4. Remaining assumptions and limitations

  - Rate limit: the guarantee rests on network jitter staying at or under 30 ms
    on the local Docker network. The provider-observed test checks this; it
    isn't proven, and it doesn't carry over to other environments.
  - Duplicates: at most one delivery per recipient and channel holds only with a
    provider that keeps idempotency keys for at least H. The mock forgets its
    keys if it restarts. If the worker is down longer than the provider keeps
    keys while a retry is pending, a duplicate can still occur.
  - Expiry boundary: an approval counts as valid if expires_at is later than the
    database clock at the moment the check runs. The boundary is now
    sub-millisecond, and a lock wait can no longer extend a TTL.
  - Unchanged from before: consent and cancellation races cover at most one
    in-flight attempt; the snapshot can be up to 24 hours stale; one worker
    replica; not exactly-once.
