  Objective: CP2 — Migration and Deterministic Seed                             
  Implement CP2 only.                                                           
  1. PostgreSQL migration                                                       
  Create:                                                                       
                                                                                
  * backend/migrations/000001_init.up.sql                                       
  * backend/migrations/000001_init.down.sql                                     
  * backend/internal/platform/db/migrations/embed.go (or the appropriate        
  location consistent with the existing project structure)                      
                                                                                
  Implement the schema specified in ARCHITECTURE.md §4.                         
  Pay particular attention to:                                                  
                                                                                
  * All tables and columns.                                                     
  * Foreign key relationships, including circular references.                   
  * Partial indexes.                                                            
  * CHECK constraints.                                                          
  * Numeric precision.                                                          
  * Nullable columns.                                                           
  * Default values.                                                             
  * Referential integrity.                                                      
  * Correct migration ordering.                                                 
                                                                                
  Do not simplify or omit schema requirements.                                  
  The down migration must reverse the up migration safely and in the correct    
  dependency order.                                                             
  Use the migration library and versioning approach specified by the            
  architecture and ADR-001.                                                     
  Migration files must be embedded in the Go application so that the API and    
  tests can access them without relying on external filesystem paths.           
  2. Turkish city catalog and normalization                                     
  Create the shared city catalog in:                                            
  backend/internal/segment/cities.go                                            
  Follow the Q4 decision:                                                       
                                                                                
  * NFC normalization using golang.org/x/text/unicode/norm.                     
  * Turkish lowercase using unicode.TurkishCase.                                
  * Fold ı to i.                                                                
  * Fold ş to s, ğ to g, ü to u, ö to o and ç to c.                             
  * Trim leading/trailing whitespace.                                           
  * Collapse consecutive whitespace.                                            
                                                                                
  The following inputs must normalize to the same canonical key:                
                                                                                
  * İstanbul                                                                    
  * ISTANBUL                                                                    
  * Istanbul                                                                    
  * istanbul                                                                    
  * Decomposed I\u0307stanbul                                                   
                                                                                
  The canonical key must be `istanbul`, and its display name must be            
  `İstanbul`.                                                                   
  Keep the catalog deterministic and suitable for later use by the segment      
  validator, prompt catalog and segment description.                            
  3. Deterministic seed generator                                               
  Create:                                                                       
                                                                                
  * backend/cmd/seed/main.go                                                    
  * backend/cmd/seed/generate.go                                                
  * backend/cmd/seed/load.go                                                    
  * Relevant unit tests.                                                        
                                                                                
  Follow the revised seed specification:                                        
  Configuration:                                                                
                                                                                
  * SEED_USERS (default 5000)                                                   
  * SEED_RANDOM_SEED (default 42)                                               
  * SEED_REFERENCE_TIME (default 2026-11-01T00:00:00Z)                          
                                                                                
  SEED_REFERENCE_TIME must be a valid RFC 3339 UTC timestamp.                   
  Use math/rand/v2 PCG with a fixed stream constant and deterministic draw      
  order.                                                                        
  Do not use:                                                                   
                                                                                
  * Global random state.                                                        
  * Current time during data generation.                                        
  * Map iteration to determine generation order.                                
  * Nondeterministic identifiers.                                               
  * Implicit database timestamps.                                               
                                                                                
  All generated timestamps must derive from SEED_REFERENCE_TIME and be          
  truncated to PostgreSQL-compatible microsecond precision.                     
  Generate the data described in the architecture, including:                   
                                                                                
  * Approximately 5,000 users.                                                  
  * Turkish names within database CHECK constraints.                            
  * Approximately 30% of users in İstanbul.                                     
  * Different İstanbul spellings in source city data, normalized to the same    
  city key.                                                                     
  * Unique phone numbers and emails, with some missing values.                  
  * A realistic mix of opted-in, opted-out and missing consent records.         
  * Some phone numbers ending in 0000 for later slices.                         
  * NULL birth_date and last_active_at values.                                  
  * Cart and purchase events spanning the preceding 90 days.                    
  * Both abandoned and recovered carts.                                         
  * Explicit consent timestamps.                                                
                                                                                
  Use pgx CopyFrom for efficient loading where appropriate.                     
  The generator must be independently testable without PostgreSQL.              
  The same SEED_RANDOM_SEED and SEED_REFERENCE_TIME must produce exactly the    
  same dataset hash.                                                            
  A different seed or reference time must produce a different hash.             
  4. Seed loading and reset safety                                              
  Implement the seed loader using the existing PostgreSQL connection            
  infrastructure.                                                               
  Behavior:                                                                     
                                                                                
  * A normal seed run must do nothing if the users table is already populated.  
  * Loading must be transactional where required.                               
  * Use deterministic insertion order.                                          
  * Ensure database-generated IDs and sequences are reproducible as specified.  
  * Log the seed inputs used for reproducibility.                               
                                                                                
  For the reset operation:                                                      
                                                                                
  * Support the `-reset` flag.                                                  
  * Refuse to reset if any campaign_deliveries rows exist.                      
  * Do not use TRUNCATE ... CASCADE.                                            
  * Delete only the customer-related data required by the architecture.         
  * Reset relevant sequences safely.                                            
  * Perform the reset and reseed in a transaction.                              
                                                                                
  Do not weaken any existing data-retention invariant.                          
  5. Makefile targets                                                           
  Extend the existing Makefile without breaking CP1 targets.                    
  Add appropriate targets for:                                                  
                                                                                
  * Running the seed.                                                           
  * Resetting and reseeding.                                                    
  * Running integration tests.                                                  
                                                                                
  Also add `seed-today`, which uses today's UTC midnight as                     
  SEED_REFERENCE_TIME.                                                          
  The default seed reference time must remain fixed and deterministic.          
  Do not add Docker Compose configuration yet. That belongs to CP8.             
  6. Test strategy                                                              
  Ordinary tests must remain Docker-independent.                                
  `make test` and `go test ./...` must continue to work with Docker stopped.    
  All PostgreSQL/Testcontainers integration test files must use:                
  //go integration                                                              
  Keep integration tests under backend/test/integration/.                       
  Unit tests must cover:                                                        
                                                                                
  * Same inputs produce identical dataset hashes.                               
  * Different random seeds produce different hashes.                            
  * Different reference times produce different hashes.                         
  * Generated values satisfy schema length constraints.                         
  * Phone and email uniqueness.                                                 
  * City normalization.                                                         
  * Expected distribution bounds.                                               
  * Every generated timestamp is at or before the reference time.               
  * Deterministic ordering.                                                     
                                                                                
  Integration tests must cover:                                                 
                                                                                
  * Migration up.                                                               
  * Migration down.                                                             
  * Migration up again.                                                         
  * Successful seed loading.                                                    
  * Database contents match the generator's canonical hash.                     
  * A second normal seed run does nothing.                                      
  * Reset is refused when campaign_deliveries contains rows.                    
                                                                                
  Use real PostgreSQL through Testcontainers.                                   
  Integration tests must fail clearly if Docker is unavailable. Do not silently 
  skip them.

  3. Seed generation and determinism

  - One math/rand/v2 PCG generator, seeded from SEED_RANDOM_SEED plus a fixed
    stream constant. Draw order is fixed per user.
  - It never reads the clock, never uses global random state, and never iterates
    a map. The phone/email maps are only used to check uniqueness.
  - Every timestamp is SEED_REFERENCE_TIME minus a whole number of microseconds.
  - The dataset hash is SHA-256 over a documented text form of all rows.
  - The default inputs always produce c553fe36…2da25. A unit test pins this
    value and the integration test checks the database against it.
  - Default dataset: 5,000 users, 8,221 consent rows, 11,042 cart events and
    3,867 purchases. About 30% are in İstanbul, spelled four ways, all stored
    under the key istanbul. About 2% of phones end in 0000.
  - The loader assigns IDs from sequences restarted to 1. Before committing, it
    reads every row back and requires the hash to match.
    - That check caught a real bug: ORDER BY channel was sorting the text column
      alphabetically instead of in enum order.

  4. Reset safety

  - Everything happens in one transaction under a seed advisory lock.
  - It locks campaign_deliveries in SHARE mode, which blocks new delivery rows
    until commit, and refuses if any row exists.
  - It then deletes purchases, cart events, consents and users in that order. No
    TRUNCATE, no reliance on cascades.
  - It restarts the sequences (I confirmed ALTER SEQUENCE … RESTART rolls back
    with the transaction) and reloads.
  - Campaign tables are never touched.

  2. Changes

  Reset safety
  - Reset now refuses with ErrCampaignsExist if any campaign exists, and still
    refuses with ErrDeliveriesExist if any delivery row exists.
  - Locking: after the seed's advisory lock, reset takes LOCK TABLE campaigns IN
    SHARE MODE and then runs both checks.
    - This waits for any campaign insert or update that isn't committed yet, and
      blocks new ones until the reset commits.
    - Approvals and deliveries both reference a campaign, so once the lock is
      held none of them can appear either.
  - I removed the old SHARE lock on campaign_deliveries. Combined with the
    campaigns lock, it could deadlock with approval preparation:
    - Prepare would hold locks on its delivery rows while waiting to update its
      campaign.
    - The seed would hold campaigns while waiting on campaign_deliveries.
    - With only the campaigns lock, the seed never waits on another lock after
      taking it, so no deadlock is possible.
  - Everything stays in one transaction. There is still no TRUNCATE, and
    campaign, content and approval rows are never deleted.

  Migration lifecycle
  - Checked against v4.19.1:
    - GracefulStop is make(chan bool, 1), is never closed, and is only read
      without blocking between migration steps.
    - So the old send couldn't actually hang or panic. But the watcher goroutine
      wasn't joined, so it could outlive withMigrator, and the code relied on
      the library's internal buffer size.
  - The new helper stopOnCancel:
    - its send never blocks (the value is dropped if no one can take it);
    - release waits until the goroutine has exited, and is safe to call twice;
    - defers run in the order watcher → migrator → database handle.
  - If creating the migrator fails, the source and driver are now closed too.
  - A cancelled run now always returns an error wrapping ctx.Err(). Migration
    semantics are otherwise unchanged.

  Docs
  - ARCHITECTURE §4 has a new paragraph on the development seed reset: the rule,
    the locking, and the recovery path (migrate down/up).
  - The main.go doc comment and the Makefile help text match it.

  3. New tests and what they prove

  - Watcher unit tests (db/migrate_test.go):
    - exactly one stop request is sent on cancellation;
    - no blocking with an unbuffered or full channel (the original hazard);
    - releasing before cancellation sends nothing;
    - 500 iterations racing cancellation against release, under -race;
    - an already-cancelled context returns context.Canceled.
  - Reset integration tests:
    a. No campaigns and no deliveries: reset succeeds and is reproducible.
    b. A campaign without deliveries: refused.
    c. Delivery rows: refused.
    d. Both refusals leave everything unchanged: dataset hash, all three
       sequences, and the campaign, content, approval and delivery row counts.
    e. Three concurrency scenarios, coordinated by polling pg_stat_activity with
       a deadline (no sleeps):
       - (a) reset blocks behind a campaign insert that isn't committed yet,
         then refuses once it commits;
       - (b) the same race, but the insert rolls back, so the reset proceeds;
       - (c) a campaign insert started during a reset waits until the reset
         commits.
  - Mutation check: with the campaigns lock swapped for SELECT 1, all three
    concurrency tests fail. This also exposed a hang in my own test (a failed
    test left a transaction open, so pool cleanup waited forever). I fixed it
    with a deferred rollback.

  4. Remaining known limitations

  - A migration file that is already running can't be interrupted. The driver
    runs statements, and its wait for the migration lock (up to 15 s), with
    context.Background(). A stop request only takes effect between files. Each
    file is transactional, so a cancelled run always leaves the schema at a
    clean version, and re-running is safe.
  - Reset waits on the campaigns lock for as long as a campaign-writing
    transaction stays open. I added no lock timeout, to keep the seed simple.
  - The plain (non-reset) seed path is unchanged. It only loads into an empty
    users table and doesn't check campaigns. A campaign created before the first
    seed would see the new users, but no IDs are reused in that case.
  - Still unverified from the last round: running the integration tests with
    Docker actually stopped (I can't stop Docker Desktop myself).
