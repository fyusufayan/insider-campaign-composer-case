  2. Objective                                                                  
  Implement a backend workflow that:                                            
                                                                                
  1. Loads an existing segmented campaign.                                      
  2. Reads its stored, validated interpretation and content brief.              
  3. Generates personalized SMS/email templates for the selected channels.      
  4. Strictly validates the output through `content.Parse`.                     
  5. Performs at most one bounded repair when output is invalid.                
  6. Atomically inserts an immutable content version and updates the campaign's 
  current content pointer.                                                      
  7. Transitions the campaign into `content_ready`.                             
  8. Safely handles concurrent campaign edits and model errors.                 
                                                                                
  The workflow must work in demo mode with NO API key and NO paid calls.        
  3. Generation contract                                                        
  Introduce a focused content generator using the existing `llm.Client`         
  abstraction.                                                                  
  Requirements:                                                                 
                                                                                
  * Support both Demo and Anthropic clients through the existing interface.     
  * Generate only content for the campaign's selected channels.                 
  * Use the validated, persisted content brief and the normalized campaign      
  rule.                                                                         
  * Never pass customer names, phone numbers, email addresses, individual       
  records or delivery rows to the LLM.                                          
  * Supply the approved variable catalog from `content.Variables()`.            
  * Explain the supported placeholder and fallback grammar.                     
  * Include field limits and worst-case personalization rules.                  
  * Explain that the message must not claim an offer or discount that the brief 
  did not authorize.

  - Prompt content_v1:
    - The variable list comes from content.Variables(), with each variable's
      maximum length.
    - It explains the {{name}} / {{name|fallback}} grammar.
    - It states the hard limits (160/80/5,000) and soft targets (150/70), and
      the worst-case length rule with a worked example.
    - It requires plain text, no invented facts, and no unsubscribe text (the
      backend adds the footer).
    - It states the offer rules.
    - The request is a JSON document inside <content_request> tags. Because JSON
      encoding escapes <, nothing in it can close the tag.
  - Schema: a closed, flat object with exactly the selected channels' fields,
    all required strings. There are three fixed variants (SMS, email, both).

  3. Strict decoding and repair

  - Decoding (ParseGeneratedContent):
    - Output is capped at 64 KiB; malformed JSON, invalid UTF-8 and trailing
      data are rejected.
    - Duplicate or unknown properties are rejected; a field for an unselected
      channel counts as unknown.
    - null or wrong-typed fields are rejected.
  - Validation:
    - Content then goes through CP11's content.Parse; there is no second
      validator.
    - Then the offer policy runs. It rejects any incentive the brief didn't
      authorize, and any money amount.
  - Stop reasons: a refusal fails without repair. A max_tokens cutoff gets one
    retry with double the budget.
  - Repair: there is exactly one repair turn, sent the structured errors. A
    second failure returns ai_output_invalid with the details and the raw
    output. At most 3 calls are made, all within one timeout.

  4. Demo generation

  - It uses fixed English templates, chosen by goal keyword, tone and length.
  - The offer is built only from its validated kind and number. No brief text is
    ever copied into the output.
  - Every combination (900 tested) is within the soft targets, passes on the
    first call and has no warnings.
  - Demo versions are stored with model = demo, and the result carries
    DemoContentNotice.
  - The demo segmentation interpreter is unchanged.

  5. Persistence and transactions

  1. The service reads the campaign without a lock and notes its version and
     channels.
  2. It calls the LLM with no transaction open.
  3. SaveContent then runs one short transaction (5 s lock and statement
     timeouts):
     - lock the campaign row;
     - read and re-validate the current version, and check it is the newest;
     - run the pure WithAIContent: version and channel check, state check,
       content must cover exactly the selected channels, numbering via
       content.NextVersion;
     - INSERT the new version row;
     - one UPDATE sets status, current_content_id and version together;
     - commit.

  The code only ever inserts or selects content rows, never updates or deletes
  them. Reads go back through content.Parse and also require normalized text and
  valid provenance. No migration was needed.

  6. State machine and concurrency

  - Allowed: segmented and content_ready; the result is always content_ready.
  - Refused with 409: draft, and pending_approval/approved (until Slice 3 can
    revoke the approval in the same transaction). sending and the final states
    are also refused.
  - No channels selected: 422 with channels/required, and the model is not
    called.
  - Concurrent edits: if the campaign changed while the model was working, the
    result is discarded as a version conflict and nothing is inserted.

    - Regression cases: free shipping alone is accepted; free shipping plus a
      discount, a percentage or a gift is rejected; no-offer text is accepted;
      no-offer plus a discount, a percentage, free shipping or cashback is
      rejected.
  - TestGenerateRepairsExtraIncentive: runs the full generator. Output with "30%
    off plus a free gift" goes to the one repair turn, and the repair message
    includes unauthorized_offer.

  Concurrent-generation test review

  TestContentGenerationConcurrent has two rounds:
  - Barrier round (the stale-version race): each generation reads the campaign
    before its model call, and all model calls are held until all 8 have
    started, so all 8 observe the same campaign version. It already asserted
    that exactly one persists. I tightened it so it now also checks that the
    other 7 are version conflicts against that one version, which makes the
    stale-version case explicit.
  - Free-running round: any interleaving, so some generations start from
    versions that earlier ones just committed and some share a version. It
    checks consistency only: version numbers are contiguous, the pointer is the
    newest row, and the campaign version moved once per stored row. It does not
    force strictly sequential fresh versions; that case is covered by the
    earlier regeneration test, which runs version 1 then version 2.

  No new integration test was needed; the existing one already covered the
  stale-version race.
