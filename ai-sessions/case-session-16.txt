  2. Objective                                                                  
  Implement this backend workflow:                                              
                                                                                
  1. A marketer explicitly starts sending an approved campaign.                 
  2. The backend validates the approval, frozen snapshot, campaign state and    
  TTL.                                                                          
  3. One atomic transaction consumes the approved approval and transitions the  
  campaign to `sending`.                                                        
  4. The persisted delivery rows become available for worker processing.        
  5. A PostgreSQL-backed worker claims eligible jobs safely.                    
  6. Immediately before a first send attempt, it checks current consent and     
  contact information according to the documented policies.                     
  7. It renders the immutable content using frozen personalization values.      
  8. It submits SMS or email to a mock provider.                                
  9. It persists each attemp

  * Rollback under injected database failure leaves consistent state.

  2. Starting a send

  POST /campaigns/{id}/send takes {approval_id, expected_version}.
  - First call → 202. It returns the campaign status and how many rows were
    released per channel, plus the campaign. No recipient data.
  - Repeat for the same approval → 200 with already_started: true. Nothing is
    written. This also applies once the campaign has finished.
  - Errors:
    - 409 for approval_expired, invalid_state, version_conflict and
      approval_mismatch
    - 404 for an unknown or foreign approval
    - 422 for an invalid body
    - 503 when the campaign is busy
    - a sanitized 500 if the frozen rows don't match the approval

  The transaction runs in this order:
  1. Lock the campaign, then the approval.
  2. Re-check expiry with clock_timestamp().
  3. Check the version and state, the approval–campaign binding, the content
     review, and the held rows (count, per-channel split and digest).
  4. Consume the approval if expires_at > clock_timestamp().
  5. Move the held rows to pending; per-channel counts must match what was
     approved.
  6. Set the campaign to sending and bump its version once.

  Any failure rolls everything back. Concurrent sends queue on the campaign
  lock: exactly one starts. Once consumed, an approval never expires, so a send
  that started in time is never cut off.

  3. Claiming, leases, crash recovery

  - Rows are claimed with FOR UPDATE SKIP LOCKED, only from the consumed
    approval of a sending campaign. Order is (next_attempt_at, id), and a claim
    never takes more rows than the pool has free slots.
  - Each claim holds a 60 s lease. The worker ID gets a random suffix per
    process start, so a restarted worker never mistakes its old leases for its
    own.
  - Recording an outcome is fenced by leased_by, in_flight and the precheck's
    dispatch_started_at, so a stale attempt can't complete a row that was
    claimed again.
  - Reaper: an expired lease with no request goes back to pending without
    counting an attempt. An expired lease after a possible request records an
    unknown attempt and schedules a retry.
  - Shutdown: the worker stops claiming, releases rows it hasn't prechecked,
    lets in-flight requests finish (up to 10 s), then aborts them and records
    them as unknown.

  4. Consent and contact checks

  - One precheck statement runs right before each request. It checks the lease,
    that the campaign is still sending and the approval consumed, and that a
    current opted_in consent row exists. A missing row counts as no consent.
  - On the first attempt the destination comes from the user's current contact.
    It must be a valid E.164 number or a plausible email address. It's saved
    before the request and reused unchanged by every retry.
  - When the precheck fails, the reason is checked in the order §10.3 lists:
    lease lost, then campaign cancelled, then skipped_consent_revoked, then
    skipped_no_contact.
  - Limit: the check only sees changes committed before it runs. A revocation
    committed between the check and the request doesn't stop that one request;
    later attempts honour it. No lock is held across the request.

  5. Frozen content and personalization

  - The approved content version is re-validated with content.Parse and must be
    in canonical form. It's rendered with RenderSMS or RenderEmail (the footer
    is always attached) using the row's frozen values, decoded strictly.
  - A render failure marks the row failed with the render code. No provider
    request is made and no attempt is recorded. Nothing is truncated or
    replaced.
  - Audience membership is never re-evaluated, and the LLM is never called
    during delivery.

  6. Mock provider

  - It's a separate HTTP service on the Compose network, with no host port.
    Endpoints are /v1/sms and /v1/email, and requests are validated strictly.
  - Idempotency ledger:
    - Same key and same payload: 200 with the original message ID and
      Idempotent-Replayed: true. Nothing is sent again.
    - Same key and a different payload: 422 idempotency_key_reuse.
  - Injected faults: random but seeded 5xx, 429 with Retry-After, timeouts that
    record the message before stalling, and permanent rejection for destinations
    ending 0000.
  - "Accepted" only means the mock recorded the message in memory. /admin/stats
    returns counters only; message text and destinations are never logged or
    exposed.

  7. Attempts and status

  - Outcomes are recorded as accepted, replayed, rate_limited, transient_error,
    timeout, unknown or permanent_error. Row status and attempt outcome are kept
    separate: skips and render failures have no attempt row.
  - A row ending in a non-sent terminal state after any ambiguous attempt is
    flagged outcome_uncertain.
  - A retry for a campaign that's no longer sending becomes cancelled.

  8. Completion

  A single statement moves a sending campaign to completed, or to
  completed_with_failures if any row failed. It only does so when every row of
  the consumed approval is terminal and the total equals the snapshot count. It
  bumps the version once; concurrent attempts produce exactly one transition.

⏺ I haven't built the durable ledger. The architecture explicitly limits the
  mock's idempotency to one process lifetime, and your instructions said to

  1. Is the in-memory ledger a violation?

  Not of the documented design. §10.6, §18 and ADR-020 all say the ledger is in
  memory, kept for the process lifetime, and that "restarting the mock provider
  forgets keys".

  CP16 did overclaim, though. I mapped "process lifetime" to an infinite
  retention, so the worker logged an unconditional "at most one delivered
  message". That contradicts §18. The README and my §10.12 text said the same.

  Your four-step sequence really does produce a duplicate.
  TestMockProviderRestartForgetsKeys runs it: the provider accepts, the response
  is lost, the provider restarts, the worker retries with the same key. The
  retry is accepted as a second message instead of replayed, so there are two
  logical acceptances.

  So the crash-recovery guarantee holds for worker crashes but not for provider
  restarts while a retry is pending. That case falls back to at-least-once.

  2. Storage and restart behaviour

  Nothing changed: the ledger is still in memory. Recreating or restarting the
  container still clears it.

  What I'd recommend: an append-only file ledger on a named Compose volume.
  - No new infrastructure or dependency.
  - Contents: one line per accepted message — key, channel, a hash of the
    payload, message ID. No contacts or message text.
  - Atomic and durable: under the existing lock, write and fsync the line, then
    insert into the in-memory map, then reply 202. A failed write returns 503
    and records nothing.
  - Crash-safe: a half-written last line is ignored on restart, which is safe
    because it was never acknowledged.
  - Survives: restart and container recreation.
  - Cleared only by: POST /admin/reset or docker compose down -v.
  - Paperwork: an amendment to ADR-020 and §10.6/§18, and the mock would then
    declare durable retention.

  The alternative is a separate PostgreSQL database for the mock. Atomicity
  would come free from INSERT … ON CONFLICT, but it couples the mock to the
  app's database server and needs an extra setup step.

  2. Durable acceptance semantics                                               
  The following invariant must hold:

  same idempotency key and identical canonical payload must return the original 
  message ID even after the provider process or container restarts.             
  Requirements:                                                                 
                                                                                
  * Persist the idempotency key, canonical payload fingerprint, channel and     
  original message ID.                                                          
  * Never store raw recipient destinations or message text in ordinary ledger   
  records if a hash suffices.                                                   
  * Persist acceptance durably before returning success.                        
  * Atomically coordinate persistence and the in-memory index.                  
  * Same key + same canonical payload → replay original message ID, with no     
  second acceptance.

  * Concurrent identical requests → exactly one acceptance.                     
  * Fail closed on storage errors; no accepted response without durable state.  
  * Preserve deterministic fault-injection behavior, including a committed      
  acceptance followed by a lost or delayed HTTP response.

  container recreation preserve it.

  1. Ledger format and commit point

  The ledger is a single append-only file at MOCK_LEDGER_PATH:
  - Header: the bytes MPLEDGER plus a format version.
  - Each record: a 4-byte marker, the record length, a small JSON payload, and a
    CRC-32C checksum.
  - Payload: sequence number, idempotency key, channel, a SHA-256 fingerprint of
    the request (channel, destination, subject, text) and the original message
    ID. No destination or message text is stored; a test checks the file bytes
    for this.

  Commit point: a message counts as accepted only once its record is fully
  written and fsync has returned. Only after that does the key go into the
  in-memory index and the provider reply 202. The lookup and the write happen
  under the same lock, so 32 identical concurrent requests produce exactly one
  record and one acceptance.

  2. Startup recovery and corrupt files

  - On start the provider takes an exclusive file lock (a second process on the
    same file is refused) and rebuilds the index from the committed records.
  - Interrupted write: if the file ends in a partial record (fewer than 8 bytes,
    or a record whose stated length runs past the end of the file), that write
    was never acknowledged. It is cut off, the cut is fsynced, and the byte
    count is logged. That key is then accepted fresh on its next request.
  - Corruption: anything else stops the provider from starting:
    - a bad checksum, marker or length
    - a gap in the sequence numbers or a duplicate key
    - an unknown field in a record
    - a file shorter than its header
    - extra bytes or zeros after the last record

    The error message is sanitized, the file is left untouched, and the provider
    never starts with an empty ledger. Because the worker waits for the
    provider to be healthy, the worker doesn't start either.

  3. Replay guarantees across restarts

  - Same key and same request: returns the original message ID with
    Idempotent-Replayed, both within one process and after restarts.
  - Same key with any changed field: returns 422 idempotency_key_reuse, also
    after restarts.
  - Message IDs keep counting from the last committed record, so they never
    repeat.
  - The worker now logs this guarantee: at most one delivered message per
    campaign, user and channel, while the provider's durable ledger is kept and
    intact and the provider behaves as declared. Requests to the provider are
    still at-least-once, and this is not exactly-once.
  - The provider now declares its key retention as "until explicit reset".

  4. Disk failures

  - If a write or fsync fails, the provider answers 503 storage_unavailable,
    which the worker treats as a temporary error, and refuses every further
    acceptance until it restarts.
  - On restart, the file decides whether that record actually committed. If it
    did, the worker's retry gets a replay, never a second acceptance.
  - Not covered: corruption the checksum can't detect, disks that ignore fsync,
    filesystems without proper locking (some network filesystems), or losing the
    volume itself.

  5. Docker volume and reset

  - The new named volume mockledger is mounted only in the mock provider
    container. The image creates /var/lib/mockprovider owned by the app user, so
    it works with the read-only root filesystem.
  - Normal operations keep the ledger: I checked restart, --force-recreate and
    down/up; the ledger held 207 records through all of them.
  - What deletes it: docker compose down -v (make reset-volumes), which also
    deletes the database. The other way is POST /admin/reset, which only works
    when MOCK_ADMIN_RESET_ENABLED=true; Compose sets it to false. Either one
    forgets every earlier key.
  - Port: no host port is published for the mock provider.
  - Repeatable smoke runs: smoke-send.sh now checks the provider's records for

    stats endpoint. It requires the ledger count to fall between the number of
    sent rows and sent plus uncertain rows. The per-process counters reset to 0
    on restart; messages counts the durable ledger.
